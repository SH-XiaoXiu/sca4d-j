# 文档审查与完成标准

## 适用范围

本规则适用于 README 和 `docs/` 中新增、修改、移动、合并和退役的页面。

## 文档类型

每个页面只能选择一种类型：

| 类型 | 回答的问题 | 推荐结构 |
| --- | --- | --- |
| Tutorial | 用户如何完成一个任务？ | 目标、前置条件、操作步骤、运行结果、下一步 |
| Concept | 功能或设计是什么？ | 是什么、为什么存在、工作原理、示例 |
| Reference | 具体参数和接口是什么？ | 接口或配置、说明、示例、限制条件 |
| Specification | 实现必须遵守什么？ | 适用范围、规则、约束、示例、验收要求 |

教程不展开设计理念；Specification 不描述学习过程；Reference 不讨论项目愿景；配置页面不解释无关的设计取舍。

## 内容完整性

改写或重组页面前，列出原文中的规则、条件、例外、失败结果、示例、代码块、链接和验收要求。每项内容必须在修改后的页面或明确的新位置中保留。

不得使用摘要替代仍然有效的详细要求。发现原文与当前代码不一致时，从源码、配置或运行结果核对正确内容，并修正文档。

## 面向读者

每一段文字至少回答一个问题：

- 用户需要知道什么？
- 用户需要执行什么操作？
- 操作成功或失败后会发生什么？
- 用户如何定位并解决问题？

删除写作过程、对读者学习过程的描述、内部分析、任务对话、执行记录、设计辩解、产品宣传和没有实际信息的总结。Agent 角色、执行规则和提示词只写入“AI 协作”章节。

禁止使用“本文将带你”“接下来深入了解”“全面掌握”“让我们一起探索”“值得注意的是”等自我说明。

## 用词

标题必须说明查询对象或操作任务，例如“配置数据库连接”“创建第一个用户”“添加文件上传”。

没有对应代码、配置、API、用户操作或运行结果时，不使用“闭环”“口径”“抓手”“赋能”“体系化”“方法论”“价值链”“基座”“能力沉淀”“统一治理”“端到端”“全链路”“最佳实践”等词。

优先使用已有行业术语和项目中的类型、接口、配置键与路由，不为文档创造新的抽象名称。

## 与代码一致

| 文档内容 | 核对位置 |
| --- | --- |
| HTTP 路由、请求和响应 | Controller、OpenAPI |
| 配置键和默认值 | Properties、YAML、`.env.example`、Compose |
| 接口和注解 | Java、TypeScript 源码 |
| 枚举和状态 | 枚举、数据库约束、Flyway 迁移 |
| 命令和产物 | Gradle、pnpm 脚本、构建输出 |
| 模块和目录 | 当前工作树 |

旧页面、规划稿和代码注释不能作为准确内容的唯一来源。

## 示例

所有示例必须包含运行所需的上下文、代码、配置和操作步骤。禁止使用“省略部分代码”“其他配置类似”“自行实现”等内容代替关键步骤。

示例不能调用不存在的接口、类型或配置。无法提供完整示例时，删除示例标题并改为准确的接口说明，不提交占位内容。

## 导航和布局

- 长期页面必须出现在侧边栏，或由侧边栏页面直接链接。
- 上一页和下一页顺序符合实际阅读关系。
- 站内搜索可以找到页面标题和主要类型名。
- 内部链接不能指向已经删除的路径。
- 桌面、紧凑桌面、平板和手机均无横向溢出或内容遮挡。
- 明暗主题下表格、代码块、链接和键盘焦点清晰可见。

## 必须通过的检查

```bash
cd docs
pnpm docs:build
```

构建通过后，检查修改页面及相邻页面的导航、搜索、代码块滚动、表格和窄屏菜单。只运行构建不能代替页面检查。

## 完成条件

- 页面类型明确，章节没有混入其他文档类型。
- 原有有效内容全部保留或移动到明确位置。
- 名称、参数、操作步骤和失败结果与当前代码一致。
- 示例完整，不包含占位说明。
- 导航、内部链接、搜索、桌面和窄屏布局均已检查。
