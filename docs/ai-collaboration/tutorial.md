# 使用 AI 交付可维护代码

## 目标

使用一个 Goal 任务提示词完成计划确认、代码实现、人类文档更新、全文件审查和一次提交。最终代码必须满足以下结果：

- 后续修改可以沿用现有业务名称、工程结构和验证方式；
- 长任务可以根据明确的 Goal、进度和剩余事项持续推进；
- 任何工作批次结束后，维护者都能根据仓库内容和状态记录人工接管。

## 前置条件

- 已准备可以读取项目文件和运行命令的 AI Agent。
- 当前仓库分支和未提交修改已经确认。
- 用户可以回答业务取舍并验收最终结果。
- 已打开[Goal 任务提示词模板](./prompt-template)。

## 操作步骤

### 1. 写明项目背景

说明当前系统、目标用户、相关模块和已经存在的实现。背景只写本次任务需要的信息，不复制整个 README。

同时记录当前运行状态，例如服务是否已经启动、使用的端口、可用的数据库和不能重建的数据。Agent 应先验证这些信息，不重复启动已有服务。

### 2. 定义最终目标

最终目标描述用户可以观察到的结果，而不是类名或文件修改。例如：

```text
平台管理员可以为一个 Account 增加 EMAIL_CODE 登录方式；
用户提交邮箱验证码后建立与密码登录相同的 Session；
管理员可以查看和停用该登录方式；
现有密码登录行为保持不变。
```

随后写明不做的内容、失败结果、兼容要求和验收方式。无法验收的目标需要继续拆解。

### 3. 提交提示词并只允许调查

把完整提示词交给 Agent。第一阶段只允许读取项目、验证当前状态、发现冲突和提出问题，不允许修改文件。

Agent 必须给出包含数据、接口、页面、失败处理、测试和文档的计划。用户逐项确认最终结果和关键取舍后，再明确要求进入实现。

### 4. 按计划实现

Agent 按可以独立验证的结果推进。每完成一项，运行最小且相关的检查。例如：

| 修改范围 | 检查 |
| --- | --- |
| Java 后端 | 受影响模块编译和测试、Spotless 检查 |
| 数据库 | Flyway 迁移校验、Repository 或集成测试 |
| 管理端 | typecheck、单元测试、构建和浏览器检查 |
| OpenAPI | 重新生成类型并运行契约检查 |
| 文档 | VitePress 构建、链接和页面布局检查 |

实现与计划不一致时，Agent 先说明差异。用户确认前，不把新方案继续扩散到其他文件。

### 5. 维护人类文档

Agent 根据[变化与维护位置](/documentation/change-routing)列出受影响页面，然后执行以下步骤：

1. 确定每页的目标读者和唯一文档类型。
2. 保存修改前内容，列出规则、条件、例外、失败结果、示例、代码块、链接和验收要求。
3. 从 Controller、OpenAPI、Properties、YAML、迁移、源码和构建脚本核对当前行为。
4. 使用项目用户和维护者的语言改写正文，不写 Agent 思考、任务对话、执行记录、临时提示词或设计辩解。
5. 不使用没有对应代码、配置、API、操作或运行结果的抽象词。
6. 保证示例包含必要上下文，不使用省略代码、类似配置或自行实现代替关键步骤。
7. 对照修改前清单，确认所有有效内容仍在原页面或明确的新位置。
8. 更新导航和内部链接，运行 VitePress 构建。
9. 检查桌面、紧凑桌面、平板、手机和明暗主题下的页面。

AI 协作章节可以包含 Agent 角色、执行规则和可复用提示词。其他章节只保留用户理解、使用和维护项目所需的内容。

### 6. 执行全文件审查

Agent 列出本次 Goal 的全部改动文件，逐个读取完整内容，并按提示词中显式列出的 34 篇项目规范检查。

发现一项不符合时，本次实现未通过。Agent 修复问题、重新运行相关检查并再次审查，直到问题数量为零。

### 7. 检查人工接管信息

AI Coding 改变了代码由谁写下，却没有改变[作者的话](/author-note/)中的两项要求：

> API 不是实现细节。
>
> API 是项目内部的业务语言。

> 这些重复，都是架构的一部分。
>
> 它们让新人知道一个功能应该放在哪里，让维护者知道一个模块应该如何扩展，让项目在多人协作中仍然像一个人写出来的。

当 Agent 也沿用同一套目录、命名、API 和调用方向时，工程师接手后不需要先辨认哪些代码由 AI 编写，也不需要恢复生成过程。代码本身仍然使用项目语言；Goal、验证结果和剩余事项只负责标明工作进行到了哪里。

提交前要求 Agent 输出：

```text
Goal：
已确认决定：
已完成：
剩余工作：无
修改文件：
验证命令及结果：
规范审查问题：0
已知限制：
```

维护者应能根据这份信息和当前工作树复查结果，并从第一项剩余工作继续处理，不需要恢复此前对话。存在剩余工作、失败命令或未确认决定时，不进入提交。

### 8. 创建提交

确认改动范围只包含本次 Goal，运行 `git diff --check` 和最终验证命令，然后允许 Agent 创建一次提交。提交说明写明用户结果、主要技术修改和验证结果。

## 运行结果

一个提交包含完整实现、测试、人类文档和验证证据。代码遵守项目已有结构和业务语言，后续任务可以继续使用同一套规则推进。项目维护者可以从提交、文档、测试和工作批次记录中理解必要决定，不依赖任务对话即可接管。

## 下一步

新任务使用新的 Goal 提示词。不要在已经通过的 Goal 中追加无关需求；需要扩展时重新确认范围和验收条件。
