# AI 协作

使用 AI 修改 Sca4d-J 时，任务需要说明目标、修改范围和验收结果。根 `AGENTS.md` 规定代码修改、方案确认和验证要求；修改文档时还要读取 `docs/AGENTS.md` 和[文档规范](/standards/13_documentation)。

给出文件、接口、报错或复现步骤后，让 AI 从这些位置调查。已经确认的业务规则直接写进任务，日志中的密码、令牌、个人资料和连接凭据先去除。

## 提供具体问题

问题原因尚不明确时，先要求分析当前行为，并明确是否允许修改文件。实际结果、预期结果和报错原文应放在同一条任务中。

例如：

```text
检查 PUT /me/profile 的邮箱修改。
预期：资料和 Account 登录标识一起更新；邮箱冲突时两者都不变化。
先读取 Controller、Service、Repository 和相关测试，说明当前行为。
本次只分析，不修改文件。
```

## 安排实现任务

规则已经确认、修改范围明确时，可以直接要求实现。例如：

```text
修复 PUT /me/profile 修改邮箱后的登录标识同步。
邮箱修改成功后，新邮箱能定位到原 Account，旧邮箱不再用于该账号登录。
清空邮箱时删除对应 EMAIL Identifier。
邮箱冲突或任一写入失败时，资料和登录标识都保持原值。

允许修改 apps/sca4d-server 中的资料服务和相关测试，使用 IAM 公开接口。
验证成功修改、清空邮箱、邮箱冲突与事务回滚。
保留工作区已有修改，完成后报告 diff 和检查结果，不创建提交。
```

任务较大时，先完成一个可独立验证的功能，再继续下一项。每次交付都应能说明哪些业务行为已经改变、哪些检查能证明结果。

## 确认会影响业务的决定

公共 API、模块依赖、认证权限、数据库结构、部署或协议变化，按根 `AGENTS.md` 先确认计划。计划需要列出涉及文件、接口与数据变化、失败结果和验证方法；存在不同业务结果的选择时，要求解释各自影响。

开发单个应用时，业务规则优先留在 `apps/`。确实需要修改公共部分时，应说明现有公开接口缺少什么，以及改变后其他应用会受到什么影响。

## 评审修改

评审任务写明文件或 diff 范围，并说明只报告问题还是同时修复。例如：

```text
只评审本次账号资料修改的 diff，不修改文件。
检查邮箱唯一性、IAM 调用、事务回滚和已有测试是否覆盖失败情况。
按严重程度列出问题，注明文件位置、触发条件和实际影响。
没有发现问题时直接说明，并列出尚未验证的行为。
```

评审时先看数据与行为：权限在哪里检查、哪些写入共同回滚、并发冲突怎样返回、外部操作重复后会发生什么。再检查命名、分层、注释和测试。代码评审范围见[评审规范](/standards/12_review)。

## 验收与交接

要求 AI 列出实际执行的命令和结果。编译检查类型和依赖，测试检查覆盖到的业务行为，页面视觉和操作体验由开发者人工验收。AI 仅在任务明确要求时启动浏览器或执行 E2E。检查范围与资源限制遵守[测试规范](/standards/11_testing)。

修改文档时，给出目标页面和读者需要完成的任务。使用 `tech-doc-style-chinese`，核对当前类型、配置和真实操作，保留条件、限制和失败结果；文章结构根据主题安排。

交接包含完成内容、未解决的问题、检查结果和必要的下一步。没有运行的检查写明原因；没有实际观察到的结果不能写成“已通过”。

提交、合并、推送和部署分别授权，并写明目标仓库、分支或环境。完成代码修改后，先检查 diff 和验证结果，再决定是否执行这些操作。
