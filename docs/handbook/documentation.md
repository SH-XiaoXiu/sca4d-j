# 更新项目文档

## 目标

随代码修改更新对应的 VitePress 页面，保留原有有效内容，并通过构建、链接和页面布局检查。

## 前置条件

- 已列出本次修改涉及的用户行为、配置、路由、类型、数据库和运行方式。
- 已阅读[变化与维护位置](/documentation/change-routing)和[文档审查与完成标准](/documentation/review)。
- 当前文档已经保存，可以与修改结果比较。

## 1. 保存内容清单

修改每个页面前，记录其中的：

- 规则、条件和例外；
- 成功与失败结果；
- 参数、默认值和限制；
- 示例、代码块和命令；
- 内部链接和外部链接；
- 验收要求。

页面拆分或合并时，为每项内容记录新的位置。不能用简短摘要替代仍然有效的详细说明。

## 2. 查找受影响页面

| 变化 | 主要位置 |
| --- | --- |
| 项目身份、启动入口、顶层模块 | `handbook/` |
| 应用组成、请求处理、身份、权限、数据和多实例运行 | `architecture/` |
| 功能实现步骤和完整示例 | `development/` |
| 必须遵守的工程规则 | `standards/` |
| 多个业务模块使用的公共接口和实现 | `infrastructure/` |
| 配置、构建、部署、观测和故障处理 | `operations/` |
| 配置键、路由、接口、枚举和错误码 | `reference/` |
| Agent 执行规则、教程和提示词 | `ai-collaboration/` |

一项内容只在主要页面完整说明。其他页面保留当前任务需要的说明，并链接到主要页面。

## 3. 确定文档类型

每个页面只选择一种类型：

- Tutorial：完成一个任务，包含目标、前置条件、操作步骤、运行结果和下一步。
- Concept：解释功能或设计，包含是什么、为什么存在、工作原理和示例。
- Reference：列出接口、配置、参数、示例和限制条件。
- Specification：定义适用范围、规则、约束、示例和验收要求。

一个页面需要同时承担多种类型时，把内容移动到对应分类，并更新内部链接。

## 4. 从当前项目核对内容

- 路由、请求和响应从 Controller 与 OpenAPI 核对。
- 配置从 Properties、YAML、`.env.example` 和 Compose 核对。
- 枚举、接口和默认值从当前源码核对。
- 数据库内容从 Flyway 迁移、Entity、Mapper 和 SQL 核对。
- 命令从 Gradle 和 pnpm 脚本核对。

旧页面、规划稿和注释不能作为当前名称或默认值的唯一来源。

## 5. 编写正文和示例

正文直接说明用户需要知道的内容、操作、结果或故障处理。删除写作过程、任务对话、执行记录、宣传文案和没有实际信息的总结。

示例必须包含必要代码、配置和步骤。不能使用“省略部分代码”“其他配置类似”“自行实现”代替关键内容。

## 6. 更新导航和链接

新增长期页面时，在 `docs/.vitepress/config.mts` 的对应侧边栏加入入口。标题说明查询对象或操作任务。

检查被修改页面、引用它的页面、上一页和下一页。删除或改名的路径不能留下失效内部链接。

## 7. 运行检查

```bash
cd docs
pnpm docs:build
```

构建后检查：

- 桌面、紧凑桌面、平板和手机布局；
- 明暗主题；
- 表格和代码块的横向滚动；
- 键盘焦点和链接名称；
- 侧边栏、上一页、下一页和站内搜索。

## 8. 对照修改前清单

逐项确认原有规则、条件、例外、失败结果、参数、示例、链接和验收要求仍在原页面或明确的新位置。任何一项缺失都需要继续修改。

## 运行结果

代码和文档描述同一个版本，新增页面可以从导航访问，原有有效内容全部保留，内部链接和 VitePress 构建通过。
