# 脚手架选型与扩展参考

## 适用范围

以下规则用于评估：

- 新项目是否采用 Sca4d-J；
- 新项目是否应直接采用微服务；
- 业务项目是否需要增加 `PrincipalType`；
- ACL 是否需要独立资源表；
- 业务项目是否需要增加 API 根路径分类。

已上线系统的服务拆分和数据迁移需要单独确定表归属、调用协议、发布顺序和恢复方法，不属于新项目选型。

项目采用不同方案时，必须记录业务现状、限制条件、预计成本和维护负责人。

## 支持的系统结构

Sca4d-J 默认提供模块化单体结构，并支持同一应用多实例部署。所有 `sca4d-server` 实例运行同一个应用产物，并连接共享的 PostgreSQL、Redis，以及启用时的 RabbitMQ 和对象存储。

| 项目 | 支持的实现 | 不提供的实现 |
| --- | --- | --- |
| 构建和发布 | 所有业务模块随 `sca4d-server` 一起构建、发布和回滚 | 业务模块独立发布和独立回滚 |
| 数据事务 | PostgreSQL、Flyway、本地数据库事务、乐观锁和 Outbox | 跨服务事务和分布式事务协调器 |
| 水平扩展 | 部署多个相同的 `sca4d-server` 实例 | 按业务模块独立扩缩容 |
| 身份和权限 | Subject、Account、Session、Principal、角色、权限和数据访问范围 | 服务间身份传播和服务间授权协议 |
| 消息和实时通信 | RabbitMQ、Outbox、SSE、WebSocket、STOMP、通知和即时通信 | 服务注册、服务发现和服务网格 |
| 后台任务 | Quartz JDBC JobStore、系统 Job 和业务 Schedule | 独立调度服务 |
| 流量入口 | 可选 Gateway、readiness 检查和静态 upstream 热更新 | 根据服务名发现和调用业务服务 |
| 管理端 | OpenAPI TypeScript 类型和 Vue 管理端 | 低代码页面和第三方长期兼容 SDK |

多个 `sca4d-server` 实例仍属于一个应用。增加实例只增加容量和节点冗余，不会形成独立的业务服务。

## 采用 Sca4d-J

Sca4d-J 适合同时符合以下情况的项目：

1. 核心业务可以作为一个应用构建、发布和回滚。
2. 一次核心写操作可以在一个进程和一个 PostgreSQL 事务中完成；事务提交后的外部操作可以通过 Outbox 或提交后消息执行。
3. 主要业务数据可以由一个 PostgreSQL 集群管理。
4. 所有主应用实例可以运行相同的代码和配置结构。
5. Subject、Account、Session、Principal、角色、权限和数据访问范围可以作为项目统一的认证授权模型。
6. 项目不要求业务模块独立发布、独立扩缩容或使用不同的运行时。

需要登录、平台管理、租户管理、管理端、文件、消息、实时通信、操作日志、并发控制或集群调度时，可以直接使用对应的内置功能。未使用的可选功能按配置关闭，不需要为每项功能单独部署一个业务服务。

## 微服务选型参考

微服务把一个系统拆成多个独立构建、发布和运行的服务。服务之间通过网络调用或消息交换数据，因此需要处理超时、重试、重复消息、数据同步、监控和故障恢复。

新项目通常先使用模块化单体。一个 `sca4d-server` JAR 可以运行多个实例，也可以部署到多个可用区。高可用、多实例、Kubernetes、集中日志和链路追踪都不要求把业务拆成多个服务。

### 新项目直接采用微服务

新项目出现以下情况时，可以评估是否把相关功能做成独立服务：

- 项目需要连接多个已经独立运行的系统，并且这些系统由不同团队维护；
- 法规、数据分级或合同要求某些数据使用独立进程、网络或数据库；
- 外部平台、设备协议或运行环境要求某个功能单独部署，并且该功能不能随 `sca4d-server` 一起运行。

决定拆分前，逐项回答下表中的问题：

| 检查项 | 需要回答的问题 |
| --- | --- |
| 维护人员 | 哪个团队负责开发、发布、值班和故障恢复？ |
| 数据 | 每张表由哪个服务写入？其他服务通过什么 API 或消息读取？ |
| 调用 | API 和消息包含哪些字段？超时、失败、重复和延迟如何处理？ |
| 发布 | 服务能否单独构建、测试、发布和回滚？兼容旧调用方多长时间？ |
| 运行 | 谁负责容量、健康检查、日志、指标、告警和安全配置？ |
| 成本 | 拆分能减少什么具体问题？新增多少部署、联调和值班工作？ |

这些问题没有明确答案时，先在同一个应用中使用独立包和依赖检查隔离业务代码。

### 从模块化单体拆分

评估已上线系统时，一次只检查一个准备拆出的模块，并记录以下数据：

- 选定一个覆盖多次发布的统计周期，记录起止日期、发布次数、发布等待时间和跨团队变更冲突；
- 该模块的 CPU、内存、数据库和消息负载，以及单独扩容预计减少的资源成本；
- 该模块故障影响其他功能的次数、持续时间和原因；
- 拆分后由哪个团队独立开发、发布、值班和处理故障；
- 需要迁移的表，以及拆分后每张表由哪个服务写入；
- 需要改成网络调用或消息的 Java 方法，以及超时和失败时返回什么结果；
- 拆分、双写或迁移、联调、监控和值班增加的工作量。

如果多个服务仍由同一批人修改、联调和发布，或者一次核心写操作仍需要同时修改多个服务的数据库，拆分通常只会增加调用和维护工作。

### 不足以支持拆分的情况

以下情况本身不足以支持微服务拆分：

- 核心业务尚未上线或仍在频繁试错，只是预计将来用户很多；
- 只有一个团队或几个共同维护同一业务的小组；
- 请求量较高、需要高可用、多实例、多可用区或集群部署；
- 准备使用 Kubernetes、集中日志、链路追踪、Redis、RabbitMQ 或对象存储；
- 业务模块、数据库表、代码文件或开发人数增加；
- 希望缩短目录、减少单个模块代码量或使用流行技术。

请求量问题可以先通过压测检查 SQL、索引、缓存、异步处理和多实例部署。发布问题可以先检查测试时间和发布流程。代码数量问题可以通过包结构、模块依赖和构建检查处理。评估记录应比较这些方案与服务拆分的实施和维护成本。

## PrincipalType

`PrincipalType` 表示当前请求由哪类主体执行。它不表示岗位、角色、会员等级或业务资料。

| 类型 | 使用位置 | 限制 |
| --- | --- | --- |
| `SYSTEM` | Quartz Job、清理任务、Outbox 投递等没有登录用户参与的后台任务 | 不能表示平台管理员，也不能用于跳过资源访问检查 |
| `DEFAULT` | Subject 的普通业务请求，不使用平台或租户工作区 | 客户等级、员工岗位等属性存入业务 Profile，不增加主体类型 |
| `PLATFORM` | `/mg/platform` 和 `/mg/system` 管理请求 | 可访问的租户和资源仍由功能权限与领域 ACL 决定 |
| `TENANT` | `/mg/tenant/tenants/{tenantId}` 请求 | 必须绑定明确的 `tenantId`；成员角色和租户层级不改变主体类型 |

同一个 Subject 可以拥有一个 `DEFAULT` Principal、一个 `PLATFORM` Principal 和多个 `TENANT` Principal。当前 Principal 只保存到本次 `CurrentRequest`，不能把工作区选择写成 Session 中的全局状态。

### 增加 PrincipalType

新增类型必须同时满足以下条件：

1. 请求代表的主体与 `SYSTEM`、`DEFAULT`、`PLATFORM` 和 `TENANT` 都不同。
2. Principal 的创建条件和请求选择输入可以明确实现。
3. 该主体需要不同的权限适用范围、资源访问规则或审计记录。
4. 该主体会用于多个业务资源或消息入口，不只用于一个接口。
5. Session 装载、`GET /me` 返回、停用和权限失效行为已经确定。

以下需求使用现有机制，不增加 `PrincipalType`：

| 需求 | 使用的机制 |
| --- | --- |
| 增加平台管理员、租户管理员或普通成员 | 角色和权限 |
| Tenant 增加父子层级 | Tenant 关系和数据访问范围 |
| 为主体增加客户、员工或供应方资料 | 通过 `principal_id` 关联业务 Profile |
| 限制一个接口可以访问的数据 | Access Policy 和 Criteria |
| 增加一个前端工作区名称 | 前端路由和导航配置；只有执行主体变化时才评估新类型 |

增加类型时，必须同步修改 Principal 创建和选择、Session、`GET /me`、权限检查、Access Policy、审计、通知和即时通信接收人、导航、OpenAPI、前端类型、测试和文档。禁止只修改枚举。

## ACL 表选型参考

ACL 记录 Principal 可以对哪些资源执行哪些操作。RBAC 检查功能权限，Access Policy 读取 ACL、资源所有者或成员关系，Repository 使用 Criteria 限制 SQL 查询和写入范围。

如果资源访问可以根据当前租户、资源所有者、成员表、业务状态或路径参数直接计算，通常不需要 ACL 表。需要由管理员单独授予和撤销资源访问权限时，再保存 ACL 记录。

### 使用独立 ACL 表

需要保存 ACL，并且存在以下任一情况时，优先使用独立表：

- 目标资源使用自己的表和 ID，删除资源时需要同时清理授权；
- 资源使用自己的动作、动作等级、默认授权或单条覆盖规则；
- 授权记录需要额外保存来源、有效期、状态或版本；
- 查询需要按具体资源 ID、动作或状态建立索引；
- 授权使用独立管理页面、审计类型或客户端刷新规则。

表名和字段直接写明资源。例如租户授权使用 `tenant_access_grant`，字段为 `principal_id`、`tenant_id` 和 `access_action`。动作、有效期和状态需要参与查询时，使用独立列，不写入 JSON。

不要为尚未实现的资源预留 `resource_type`、字符串 `resource_id`、空字段或 JSON 扩展字段。

### 使用共享 ACL

共享 ACL 表适合规则完全相同的资源。评估时检查以下内容：

1. 所有授权目标都登记在同一张资源表中，并使用同一类型的资源 ID；
2. 所有资源使用相同的 Principal 类型、动作、动作等级、默认授权和拒绝规则；
3. 所有授权使用相同的创建、替换、失效、删除清理、版本和审计处理；
4. Policy 和 Repository 不需要根据 `resource_type` 选择不同的业务表或动作规则；
5. 至少有两个已经实现的模块使用这些规则，不为将来可能增加的模块提前建表。

任一项不同时，独立表可以直接使用资源 ID 类型、索引和删除清理规则，维护代码更少。

避免以下表结构和代码：

- 使用 `principal_id + resource_type + resource_id + action` 接收所有资源的授权；
- 使用字符串或 JSON 兼容不同资源 ID、动作、期限和覆盖规则；
- 在通用 Service 中按 `resource_type` 分支查询业务表或执行删除清理；
- 为了减少表数量，把租户、文件、项目、设备等不同资源写入同一张表。

这些结构无法在写入时确认 `resource_id` 对应哪张表。删除资源、建立索引和检查动作时，还需要按 `resource_type` 增加分支。

### 常见判断

| 场景 | 选择 | 原因 |
| --- | --- | --- |
| PLATFORM Principal 需要单独获得不同租户的 `READ/WRITE/MANAGE` 上限 | 独立 `tenant_access_grant` | 表可以直接保存 tenantId、默认动作和单租户覆盖动作 |
| 租户成员、租户角色和租户字典都随目标租户范围访问 | 复用租户 ACL，不新增资源 ACL | 这些资源的范围可以由 tenantId 和租户 Criteria 推导 |
| 文件是否可读由头像、IM 或其他业务资源关系决定 | 由业务 `FileSignaturePolicy` 判断，不新增通用文件 ACL | Policy 可以直接检查文件与业务记录的关系 |
| 资源所有者始终拥有访问权，其他人不能被单独授权 | 使用 owner 或成员关系，不新增 ACL | 权限可以从已有稳定事实计算 |
| 多个模块授权同一张资源登记表中的记录，并使用相同动作和删除规则 | 可以评估共享 ACL | 资源 ID、动作、查询和清理代码可以共用 |

## API 根路径分类

API 路径首先表示资源。只有同一组资源存在不同的调用主体或管理范围时，才增加分类路径。

| 根路径 | 用途 | 当前 Principal |
| --- | --- | --- |
| `/authentication-methods`、`/authentications`、`/sessions` | 认证方式、当前认证任务和登录 Session | 创建和提交认证允许匿名；删除当前 Session 需要登录 |
| `/me` | 查询当前 Subject、固定 Account、Session、Principal、权限和导航 | 由查询参数选择 `DEFAULT`、`PLATFORM` 或 `TENANT` |
| `/system` | 查询权限、错误码等客户端目录 | `/system/permissions` 允许匿名访问；其他接口按 Controller 的认证声明执行 |
| `/mg/system` | 管理菜单、字典、操作日志和系统 Job | `PLATFORM` |
| `/mg/platform` | 管理平台 Account、操作员、租户、角色、租户 ACL 和 Schedule | `PLATFORM` |
| `/mg/tenant/tenants/{tenantId}` | 管理指定租户的成员、角色和字典 | 与路径 `tenantId` 匹配的 `TENANT` |
| `/files` | 签发文件访问信息、上传文件和读取文件内容 | 签名接口允许匿名调用；上传接口使用当前 Principal；下载接口验证短期 token |
| `/notifications`、`/im` | 使用通知和即时通信资源 | 当前请求已经选择的 Principal |

例如，平台管理租户成员使用 `/mg/platform/tenants/{tenantId}/members`，租户成员管理本租户成员使用 `/mg/tenant/tenants/{tenantId}/members`。两个接口操作同一类资源，但 Principal 选择和允许访问的数据不同。

### 增加根路径分类

新增顶层分类或 `/mg` 下的工作区分类必须同时满足以下条件：

1. 存在不同于当前主体、平台或租户工作区的固定调用方。
2. 该分类包含多个资源，不是单个接口或单个页面。
3. Principal 选择、数据访问、审计、限流或 API 兼容规则至少有一项与现有分类不同。
4. 现有资源路径、`/mg/platform`、`/mg/tenant`、权限和 Access Policy 无法表达该差异。

以下情况不增加分类：

| 需求 | 路径规则 |
| --- | --- |
| 增加面向当前 Principal 的普通资源 | 直接使用资源根路径 |
| 平台管理新资源 | 使用 `/mg/platform/{resources}` |
| 租户管理新资源 | 使用 `/mg/tenant/tenants/{tenantId}/{resources}` |
| 同一资源需要不同权限 | 保持路径不变，使用权限和 Access Policy |
| 后端包、前端页面或负责团队不同 | 保持路径不变 |
| 触发一次 Schedule 执行 | 使用执行记录资源 `/mg/platform/schedules/{scheduleId}/executions`，不增加 `/run` 动作路径 |

`PrincipalType` 和 API 根路径分类分别判断。新增主体类型后，通用资源能够根据当前 Principal 完成权限和数据检查时，不需要增加根路径分类。新增外部 API 分类但仍由现有 Principal 执行时，不需要增加主体类型。

## 评估依据

作出选择前，建议记录以下事实：

| 判断项 | 建议记录的内容 | 项目文档 |
| --- | --- | --- |
| 构建和发布 | 构建产物数量、发布周期、回滚单位 | [应用、网关和外部服务](/architecture/application-boundaries.md) |
| 数据和事务 | 每张表的写入模块、事务范围、跨模块同步方式 | [数据、事务与一致性](/architecture/data-and-consistency.md) |
| 扩缩容和故障 | 需要独立扩容或隔离的模块、压测结果、故障影响范围 | [多实例运行模型](/architecture/runtime-topology.md) |
| 微服务 | 维护团队、发布记录、压测结果、故障记录、数据写入方和拆分成本 | [应用、网关和外部服务](/architecture/application-boundaries.md) |
| 身份和权限 | Subject、Account 来源、可用 Principal、Principal 选择输入、数据访问规则 | [IAM 身份与访问模型](/architecture/iam.md) |
| ACL | Principal、目标资源、动作、默认和覆盖规则、查询条件和删除方式 | [权限与资源访问](/architecture/permission-and-access.md) |
| API 路径 | 调用方、当前 Principal、资源名称、权限和数据范围 | [HTTP 接口](/reference/http.md) |
| 内置功能 | 需要启用的消息、文件、实时通信、通知、IM 和调度功能 | [内置功能](/infrastructure/) |

无法确定构建产物、表的写入模块、事务范围、当前 Principal 或授权规则时，现有信息不足以支持架构调整。先补充业务和运行记录，再重新评估。
