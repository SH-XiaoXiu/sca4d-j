# 需求与实现设计

业务需求说明谁在什么条件下完成什么操作，以及操作后数据和状态怎样变化。采用 Sca4d-J 创建业务项目后，在 `docs/requirements/` 维护这些规则，作为开发、测试和验收的依据。

按可以独立讨论和验收的功能组织内容，例如订单、售后或设备安装。一项功能的规则、例外和验收条件放在一起；篇幅较短时可以共用一页。章节按业务展开。

## 从业务操作写到验收条件

“支持账号状态管理”还不足以指导实现：哪些账号可以停用、已有登录是否结束、失败后状态是否变化，都需要确定。以 Sca4d Server 的平台账号停用为例：

| 业务规则 | 可观察的验收结果 |
|---|---|
| 操作者需要账号管理权限 | 缺少 `platform:accounts:manage` 时返回 403，账号状态不变 |
| 不能停用当前账号或受保护的 ROOT Account | 返回 409，目标账号仍可使用 |
| 停用其他可管理账号 | 账号变为 `DISABLED`，不能再建立新 Session |
| 停用后终止目标账号的在线 Session | 使用原 Session Token 调用受保护接口失败 |
| 普通 JWT 请求离线验证 | 已签发 JWT 可能继续有效至自身过期，验收按配置的有效期检查 |

这些规则来自[平台账号 HTTP 接口](/reference/http/sca4d-server#platform-account)。具体业务有不同要求时，先确认规则，再调整实现和验收条件。

输入有单位、范围、默认值或空值含义时，一并写清。涉及状态变化时，列出允许的起始状态和目标状态。重复提交、并发操作或外部调用失败会影响结果时，写明保留哪些数据、是否重试，以及由谁继续操作。

## 把未决定的规则写成具体问题

例如，设备安装任务是否允许在已派单后取消：允许取消时，需要通知安装人员并处理已经发生的费用；不允许取消时，需要明确转人工处理的入口。把不同选择的用户操作和数据结果写出来，由业务负责人确认。

未确认的选择保留为问题。确认后，把最终规则写回对应功能，删除已经失效的备选说法。

## 从需求到实现设计

需求确定后，说明现有模块能完成哪些操作，应用还需要增加哪些接口、数据和页面。业务规则通常留在 `apps/`；需要改变公共接口或模块职责时，先说明对其他应用的影响。

以账号停用为例，设计应说明请求如何检查权限、哪个 Service 校验保护规则、账号状态写入与 Session 终止的顺序，以及任一步失败后的结果。通用分层和并发规则引用[架构与边界](/standards/02_architecture)，功能文档补充具体业务的选择。

需求与实现设计使用独立段落或文件。字段名、表名或实现类调整时，业务规则可以保持不变；业务规则变化时，同时检查接口、页面、迁移和测试。

## 验收与维护

每项验收条件对应测试、请求响应、数据库结果或人工操作。页面布局和操作体验列出人工验收动作；外部设备、真实账号或生产环境才能确认的结果，单独说明所需条件。

根 README 描述业务项目，通用开发要求引用[项目规范](/standards/01_principles)。任务进度、分支和提交记录保存在团队指定的任务记录中，需求正文保留有效的业务规则和设计。
