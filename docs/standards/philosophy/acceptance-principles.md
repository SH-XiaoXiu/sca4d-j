## 目标

提交后的代码应当稳定、可预测、语义统一，并自然延续当前项目已经形成的语言。

代码质量以长期理解成本、职责清晰度和系统一致性衡量，不以技巧、抽象数量或代码行数衡量。

## 单一语义

一个概念只保留一套业务术语、一套运行时模型和一个事实来源。

以下情况不符合单一语义：

- 同一业务字段的前后端两套计算；
- 同一状态的数据库、缓存和上下文多套来源；
- 同一请求或身份的重复上下文对象；
- 同一路由、配置和默认值的多处维护；
- 同一能力的多条旁路入口；
- 旧名称与新名称同时存在。

负责该数据的字段或 Service 是唯一事实来源，其他模块不重复计算并形成不同结果。

## 稳定核心

核心 API 保持稳定的语义、参数和行为。

业务场景差异通过外围流程表达。只有底层能力完全一致时才复用核心流程。

产品端、管理端、后台任务和外部回调在状态机、权限、副作用、审计或数据访问不同的情况下，使用独立流程，并复用真正共享的底层能力。

## 抽象价值

只抽象具有独立、准确、可复用语义的行为和概念，不抽象执行步骤。

类、接口、私有方法、Builder、Factory、Context、Manager、Helper 和包装对象只有形成独立且可复用的语义时才成立。

以下情况通常不构成有效抽象：

- 只转发另一个方法；
- 只包装一到两个基础字段；
- 只完成字段复制；
- 只把完整流程拆成 prepare、build、validate、execute、after 等步骤；
- 只为未来可能出现的需求预留扩展点；
- Mapper 和 Repository 以相同方法一一对应。

无法独立说明语义的抽象不符合验收要求，相关逻辑应保留在完整业务流程中。

## 阅读连续性

核心业务流程保持展开，使阅读者能够从上到下看到完整的校验、决策、状态变化、持久化和副作用。

较长的方法本身不是问题。为了缩短方法而增加跳转、隐藏关键顺序或分散事务语义属于质量下降。

私有方法只承载能够被准确命名和独立说明的能力。

## 项目语言

API、类型、字段、包和路由名称表达业务概念和职责归属。

process、handle、execute、data、info、context、manager、helper、util 等泛化名称只适用于已经形成明确项目含义的概念，不能代替业务名称。

Dto、Command、Result、Payload 等后缀只在对象确实承担对应职责时使用，不能仅靠后缀区分结构相同的对象。

相邻模块已经稳定重复的目录、命名、调用方式和对象结构属于架构语言。新实现应当延续这种可预测性。

## 显式契约

核心 API 优先使用显式参数和清晰类型。

一组参数已经形成稳定业务概念时可以包装；仅为减少参数数量创建的 Context、Options 或 Payload 不符合显式契约要求。

让 Java 类型、泛型、枚举和 JetBrains 注解表达可以在编译期识别的约束。

## 分层职责

每一层使用与其职责相符的语言：

- Controller 表达传输协议、请求绑定、权限声明和响应转换；
- Service 表达业务能力、规则、事务和副作用；
- Repository 表达面向业务的数据访问语义和聚合操作；
- Mapper 表达 SQL 动作、查询条件和数据库结果映射；
- Entity 表达持久化结构；
- View 表达对外响应结构和展示转换。

新增层级必须完成职责转换。Repository 不能只是 Mapper 的同名转发器，Service 不能只是 Repository 的同名转发器。

所有 Java 项目使用 `Controller -> Service -> Repository -> Mapper` 依赖方向。Service 直接依赖 Mapper、Controller 直接依赖 Repository 或 Mapper 均不符合分层要求，不因历史代码、开发阶段或项目规模设置例外。

新增、修改和重命名的文件按完整文件验收。文件中原有的不合规实现同样属于本次验收范围，验收范围不能缩小到新增行。

## 持久化抽象梯度

Service、Repository 和 Mapper 使用不同层级的语言：

- Service 表达业务动作、状态机、权限、事务和副作用；
- Repository 表达稳定的持久化能力、聚合读写和持久化结果；
- Mapper 表达最小、可组合、可验证的 SQL 查询和写入形状。

同一个 SQL 形状不因业务动作名称不同而拆成多个 Mapper 方法。Repository 也不因调用方动作名称不同而创建只绑定常量参数的包装方法。

自定义 Mapper 方法数量大于或等于 Repository 公开持久化方法数量属于高风险信号。不存在一一转发、SQL 过度拆分和业务语义下沉，并且每层都完成语义压缩和职责转换时，持久化分层才符合要求。数量本身不作为验收结论。

完整规则见[持久化分层完整规范](/standards/stack/persistence-boundary)。

## 框架原生能力

优先使用成熟框架和项目已经提供的公共实现入口。

自定义解析、转换、路由匹配、序列化、缓存、消息拓扑、权限通配、对象复制和生命周期管理，只在框架或仓库没有对应标准机制时成立。

框架能力满足语义时，删除自定义替代实现。框架能力无法满足时，自定义层必须清楚表达新增语义，而不是再次包装框架 API。

## 数据事实

数据库保存稳定事实，不保存能够可靠推导的临时投影和业务变化。

计数、汇总和派生状态能够通过明确查询条件得到时，优先查询计算。只有并发、性能和一致性要求证明需要持久化投影时，才增加维护机制和失效规则。

类型系统能够表达的业务限制不转移给数据库字段命名和重复表结构。

## 多实现决策

存在稳定的多实现能力时，使用接口、策略或项目既有扩展机制集中分派。

provider、类型或模式判断集中在一个分派位置。只有一个固定实现且没有稳定扩展语义时，不增加只为形式完整而存在的接口。

## 变更一致性

功能完成意味着相关表面使用同一套最终契约：

- 源码；
- API；
- 配置；
- 数据库迁移；
- 测试；
- 文档；
- 前端或其他调用方；
- 日志、事件和通知。

重命名和边界调整完成后，源码、配置、测试和文档中不再保留旧名称、旧路由、旧配置项、重复默认值和过期说明。

## 证据优先

故障修复以实际失败路径和真实界面为验收对象。错误信息、截图、日志和 SQL 结果用于确定发生问题的调用与数据。

根因必须由日志、断点、请求记录、数据库数据、构建产物或运行时调用链证明，不能仅根据相邻代码推测。

相邻但未发生问题的页面或接口发生变化，不能作为原故障已经修复的验收证据。

## 范围纪律

变更范围包含当前功能及其必要影响面，不包含与目标无关的历史代码整理。

范围外技术债只有在直接导致当前功能错误、无法验证或破坏已确认契约时，才进入本次变更。

工作树中与当前变更无关的已有修改保持原状，不回滚、不覆盖，也不进入本次提交。

## 完成条件

新增或修改的类、接口、方法和字段必须同时满足：

1. 表达可以独立说明的业务概念或技术职责；
2. 位于负责该职责的模块和分层；
3. 没有复制项目中已经存在的概念或公共实现入口；
4. 抽取的方法或类型表达独立行为，而不是业务流程中的执行步骤；
5. 没有重复实现框架或项目现有机制；
6. 所有调用方、测试、配置和文档使用同一套当前契约。

任一条件不成立时，变更不符合本规范。
