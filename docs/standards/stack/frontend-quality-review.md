# 前端质量与交互设计完整规范

## 生效范围

变更包含前端页面、组件、样式、路由、Store、API 客户端、前端测试或构建配置时，强制执行本规范。

本规范与以下内容共同定义前端验收条件：

- [Vue、TypeScript 与交互规范](/standards/stack/frontend)；
- [管理端基础设施](/infrastructure/admin)；
- 与页面实际消费 API 对应的 OpenAPI 契约和业务文档。

管理端交互、响应式、视觉一致性和验收必须满足以下全部要求。教程和示例只能解释实现方法，不得降低这些要求。

## 完整页面审查

新增或修改页面、布局和公共组件按完整文件和实际渲染结果验收，不能只依据模板、样式 diff 或单一截图。

每个页面必须满足：

- 当前状态、页面重点和唯一主操作可以快速扫描识别；
- 查询、重置、新增、编辑、详情、删除、启停和角色变更使用统一位置、文案、图标、颜色与反馈；
- 不存在卡片套卡片、装饰性悬浮区、过度圆角、无业务意义阴影或单一色系堆叠；
- 页面区域连续展开，卡片只用于独立对象、统计项、模态和明确边界工具；
- 紧凑面板、表格和抽屉使用与容器匹配的字号和密度，不使用营销页式大标题；
- 文案使用用户业务语言，不暴露实现名、HTTP 状态或只有错误码的信息；
- 操作顺序符合用户完成业务的自然流程，不要求用户理解系统内部步骤；
- 对话框只展示完成当前决策所需的内容，不嵌套无关说明和装饰。

## 组件与目录边界

- 领域页面、领域组件和对应测试位于 `src/features/<domain>`；路由文件不得成为页面实现容器；
- 页面组件只编排请求、领域流程、路由和跨组件状态，不内联多个完整表单、对话框或可独立切换的业务视图；
- 独立流程按用户任务拆分，独立视图按稳定信息结构拆分，组件名称表达业务职责，不使用 `Content`、`Section1`、`Helper` 等无法预测内容的名称；
- 跨领域组件按操作、头像、数据展示、数据录入、导航和页面骨架分类；领域专属组件不得无条件放入公共组件目录；
- Store 按 Session、Authentication、Workspace 等稳定状态概念拆分，页面临时表单状态不得写入全局 Store；
- 路由定义按访问范围或领域拆分，根路由文件只组合路由、守卫和跨页面协调；
- 语言资源按领域与 locale 拆分，根资源只负责组合，并保持既有消息键路径稳定；
- 拆分以形成独立职责和测试边界为完成条件，不以函数行数或文件行数机械切割。

## 交互与状态

所有用户操作必须检查完整状态机：

- 请求超过 300ms 时有加载反馈；
- 提交期间阻止相同意图重复提交；
- 成功后更新当前数据和必要的全局状态；
- 失败时保留可恢复上下文，展示原因和下一步动作；
- 409 冲突不自动覆盖，必须刷新后重新确认；
- 删除、停用、覆盖等高风险动作说明对象和影响并明确确认；
- 高风险确认使用警告说明区、明确后果和危险操作按钮；普通验证或无破坏性流程使用中性说明，不得共享同一种确认视觉；
- 字段校验靠近字段，提交失败后可以定位第一个错误；
- 空状态说明原因并提供与权限和业务状态匹配的下一步动作；
- 图标按钮具有 tooltip 或无障碍名称，关键操作不依赖 hover；
- 表单步骤、按钮名称和最终结果保持一致，“下一步”不得直接完成提交；
- 服务异常使用安全提示并在有排障价值时提供 traceId，不向用户泄露内部异常；
- 界面优先做到无需说明即可使用，其次使用一次性提示，最后才增加常驻帮助。

只实现默认成功态、只显示通用 toast、使用静态假数据或未消费最终 API 的页面不符合交互要求。

## 响应式与可访问性

桌面、紧凑桌面、平板和手机必须保持相同业务能力。布局可以变化，不得删除查询、详情、编辑、确认和批量操作。

响应式与可访问性验收包括：

- 桌面表格在窄屏转换为可操作的信息卡片或等价结构；
- 筛选在窄屏使用抽屉或等价紧凑流程；
- 编辑模态在移动端使用全屏或近全屏流程，并确保软键盘不遮挡当前字段和提交操作；
- 触控目标不小于 40px，常用主操作建议 44px；
- 文本、最长业务值、按钮和表格内容没有溢出、遮挡或意外横向滚动；
- 键盘焦点、表单 label、按钮 accessible name 和对比度满足实际使用要求；
- 明暗主题使用统一语义令牌，不在页面内散落硬编码主题颜色。

## 设计令牌与样式

色彩、字号、行高、间距、边框、阴影和圆角必须来自统一令牌或项目公共样式。

设计令牌验收包括：

- 主色只用于主操作、链接、选中态和重点状态；
- 成功、警告、错误色只表达对应状态；
- 正文基准 14px，最小可识别字号 12px，中文正文行高不低于 1.4，长文本段间距不低于正文大小的 1.5 倍；
- 单页使用 3 至 5 个文字层级，相邻层级字号差保持 2 至 4px，优先使用 400、500、600 字重；
- 圆角默认 6px，独立卡片和模态最大 8px；
- 普通内容默认无阴影，阴影只表达真实空间层级；
- 模态遮罩使用深色透明层突出当前决策，不用装饰性背景争夺注意力；
- 四位以上整数按展示语义使用千分位；
- 动态内容以最长合理值验证布局稳定性。

页面局部写死颜色、尺寸或间距时，必须证明它是独立业务视觉语义；否则迁移到统一令牌。

## 文案与数据展示

- 操作文案使用“动词 + 名词”，统计文案使用“数字 + 单位 + 名词或动词”；
- 同一业务概念在入口、页面标题、表单、提示和错误信息中使用同一名称；
- 日期时间使用 24 小时制，ID、traceId 等技术字段只在确有排障价值的位置出现；
- 中文与英文、中文与表示数量的数字之间保留空格，完整英文句子使用半角标点；
- 文案必须词汇统一、语法正确、精炼、通俗且友好，避免命令式否定和无意义帮助。

## API 与数据契约

- 页面必须消费最终 OpenAPI 对应的真实 API 客户端；
- 不在前端重复推导后端已经拥有的业务字段、权限、状态或计数；
- 64 位 ID 保持字符串契约，不经过 JavaScript `number`；
- 路由、请求字段、状态枚举、错误处理和刷新目标与后端使用相同定义；
- OpenAPI 生成文件必须由运行中的当前 Server 生成并通过无漂移检查。

## 验证

前端变更至少执行：

```text
pnpm api:check
pnpm typecheck
pnpm lint
pnpm test
pnpm build
pnpm e2e
```

Playwright 必须覆盖桌面、紧凑桌面、平板和手机，并验证主要页面非空渲染、主要操作的成功与失败结果、明暗主题、横向溢出和关键内容遮挡。浏览器未安装、服务未启动或使用旧 OpenAPI 时，浏览器验收未完成。

## 不合规情况

出现以下任一情况时，前端变更不符合本规范：

- 未覆盖完整文件或违反当前前端规范；
- 修改页面未逐个实际渲染检查；
- 桌面和移动端业务能力不一致；
- 操作缺少加载、成功、失败、禁用或恢复反馈；
- 高风险操作没有明确确认；
- 空状态只有“暂无数据”且没有下一步动作；
- 关键操作只在 hover 出现；
- 页面存在溢出、遮挡、嵌套卡片或不合规圆角/阴影；
- 页面使用静态假数据、旧路由或未消费最终 API；
- OpenAPI、类型检查、lint、测试、构建或 E2E 任一未通过；
- 前端改动文件、页面或 viewport 仍有未验收项。
