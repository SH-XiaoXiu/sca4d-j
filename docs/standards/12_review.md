# 12 代码评审覆盖规范

评审先确定全部改动文件，再逐个阅读完整内容，沿调用方核对业务结果、分层、失败和并发。每个结论都对应文件位置与验证证据；未读文件、未执行检查和未确认行为必须明确列出，不能用抽样或编译成功代替完整评审。

## 覆盖范围

一次完整代码评审包含以下内容，缺少任一项都视为覆盖不完整：

1. 最终需求、确认方案、仓库规范和相关专题文档；
2. 使用 `git status --short`、`git diff --name-status -M <base>` 和 `git ls-files --others --exclude-standard` 建立全部改动文件库存。
3. 确认 staged、unstaged、untracked、rename 和 deleted 文件均已进入库存。
4. 逐个打开每个新增、修改和重命名文件的完整内容，不只阅读 diff hunk；删除文件读取删除前完整内容并检查消费者清理。
5. 对 Java 文件执行分层依赖、公开 API、私有方法、框架使用、注释和测试审查。
6. 对 SQL、Mapper、Repository 和持久化 Service 完整执行[持久化分层完整规范](/standards/05_persistence)。
7. 对列表、分页、循环和批处理量化数据库与外部调用次数，检查 N+1 和可批量化操作。
8. 对状态迁移、任务、消息、缓存、锁和外部副作用证明集群并发、重复执行与失败恢复成立。
9. 沿改动契约检查必要消费者、配置、迁移、测试和文档。
10. 前端变更逐页面执行[前端质量完整规范](/standards/07_frontend)，按实际影响选择静态检查与核心业务测试，并记录实际检查的页面、操作和状态。
11. 覆盖数据、全部问题和验收结果。

任一项为「否」或「不通过」时，该文件不符合验收条件。

## 强制扫描

Git 库存和静态搜索只用于发现候选和证明覆盖，不能代替源码审查。覆盖证据至少包括：

- 所有改动 Java 文件数量与实际状态一致；
- 所有 Service 文件均已检查是否直接依赖 Mapper；
- 所有 Controller 文件均已检查是否越过 Service；
- 所有 Repository 与 Mapper 方法均已建立对应关系；
- 所有私有方法均已分类；
- 所有接口和接口方法均已检查文档契约；
- 所有非平凡方法均已检查中文逻辑注释；
- 所有新增类型和公共实现入口均已搜索重复实现及旁路入口。
- 所有 Entity、领域模型、Request、Result、View、Mapper 查询结果和 Service 契约的有限状态/类型/模式/操作字段均已检查类型安全枚举；
- 所有改动前端文件和页面均已完整阅读并按前端质量规范审查；
- 布局变化时列出实际受影响的尺寸，由开发者检查业务操作、溢出、遮挡和反馈；尚未实际检查的页面和尺寸必须明确列出；
- 所有列表、分页、循环和批处理均已量化 SQL 与外部调用次数并检查 N+1；
- 所有状态迁移、任务、消息、缓存、锁和外部副作用均已检查集群竞争、幂等和失败恢复。
- 所有业务阶段和必要技术边界均已检查 INFO、DEBUG、WARN、ERROR 的选择与字段完整性；
- 所有应用日志均可由 `%source` 得到模块和实际类名，消息不包含秘密、完整 Payload 或重复异常；
- 所有新增、修改和移动类型均已检查领域根包、职责子包以及 Util/Helper 的真实职责。

## 不合规情况

出现以下任一情况时，代码评审覆盖不完整或变更不符合规范：

- 没有建立包含 tracked、untracked、rename 和 deleted 文件的完整库存；
- 存在未打开完整内容的改动文件；
- 只检查新增行，没有检查改动文件原有代码；
- 使用抽样代替逐文件审查；
- Service 直接依赖 Mapper；
- 存在用 String 表达系统定义有限状态、类型、模式或操作的字段，或开放字符串标识没有说明扩展来源；
- 存在可稳定批量化的 N+1 或逐行数据库操作；
- 逻辑依赖单实例、进程锁或单机调度才能成立；
- 私有方法尚未判断是否可以准确命名并独立说明；
- 注释只检查数量，没有检查契约质量；
- 测试只验证内部实现，没有验证真实边界；
- 前端存在未审查页面、未验证 viewport 或违反前端质量规范的实现；
- 业务流程缺少阶段日志，或日志级别、字段、失败结果和敏感数据处理不合规；
- 改动类型位于不表达其职责的包，或 Util/Helper 实际执行业务流程；
- 差异规模超过当前评审能够完整覆盖的范围。

差异规模超过单次评审覆盖范围时，提交必须按可以完整审查的职责边界拆分，不能使用抽样结果代替完整覆盖。

## Java 工程完整审查规范

### 适用范围

本契约适用于所有 Java 项目，不因仓库类型、业务规模、开发阶段或历史代码质量降低标准。

所有新增、修改、重命名、删除的 Java 文件都必须审查。新增、修改和重命名文件读取当前完整内容；删除文件读取删除前完整内容，并检查所有消费者、配置、测试和文档是否同步清理。Git diff 只用于确定审查入口，不用于缩小文件内部的审查范围。

改动文件中原本已经存在的不合规代码同样属于验收范围。新增、修改和重命名的文件必须整体达到清晰、一致、可预测且符合规范的状态。

未被触及且不属于必要消费者的历史代码不进入本次范围。「历史代码」「不是本次新增行」或「后续模块再处理」不能缩小改动文件的验收范围。

### 长期质量目标

代码必须以五至十年后的维护为标准：

- 新成员能够根据目录、类型和 API 准确预测职责；
- 同类模块保持相同分层、命名、调用和异常处理方式；
- 核心流程可以连续阅读，不依赖作者记忆和当前会话背景；
- 框架、持久化和传输细节停留在所属边界；
- 注释、测试和文档表达当前有效的行为与约束；
- 不保留只能由当前作者解释的技巧、捷径和临时定义。

任一条件不满足时，代码不符合长期质量目标。

### 强制分层

Java 业务代码统一遵守以下依赖方向：

```text
Controller -> Service -> Repository -> Mapper
```

无一例外执行：

- Controller 不直接依赖 Repository 或 Mapper；
- Service 不直接依赖 Mapper；
- Service 不处理 SQL 形状、影响行数、ResultMap、Wrapper、数据库字段和关系查询拼装；
- Repository 负责稳定持久化语义、聚合加载、关系维护、结果转换、乐观锁和数据库异常边界；
- Mapper 只表达最小、可组合、可验证的 SQL 动作和数据库结果形状；
- 公共模块不依赖业务模块，不实现业务逻辑，不访问业务数据库；
- View、Request 和传输协议对象不进入 Repository 或 Mapper；
- Entity、Mapper Result 和持久化框架类型不泄漏到不应理解数据库形状的上层公开契约。

Service 直接注入、查找或调用 Mapper 不符合分层要求。Service 同时承担分页拼装、关系加载、影响行数判断或数据库异常转换时，说明 Repository 边界缺失，持久化结构必须恢复完整分层。

业务 Service 的公开方法表达完整业务契约。存在多个实现、跨模块稳定契约或应用扩展点时使用 Java interface；不要求每个 Service 机械地拆成接口与实现类。

### 全文件职责

每个改动文件必须同时满足：

1. 文件位于负责其职责的模块和包；
2. 类型只承担一个清晰职责；
3. 依赖方向符合项目分层；
4. 公开 API 使用所属层级的语言；
5. 没有绕过公共实现入口或形成第二入口；
6. 不向上层泄漏框架、数据库、传输或线程上下文细节；
7. 不存在表达同一对象的重复类型、重复计算、重复状态来源或重复转换；
8. 方法、字段、注解、异常和注释与当前契约一致；
9. 测试覆盖真实框架生命周期和边界，不只验证内部实现；
10. 代码和成品文档足以支持长期维护，不依赖当前作者或会话背景。

任一条件不成立时，文件不符合本规范。

### 类型安全状态

Java 类型系统必须表达稳定的有限集合。Entity、领域模型、Request、Result、View、Mapper 查询结果和服务契约中的状态、类型、模式、操作、类别等字段，只要取值集合由系统定义且有限，就必须使用项目统一枚举，不得降级为 `String`。

以下字段属于重点验收范围：

- `status`、`state`；
- `type`、`kind`、`category`；
- `mode`、`operation`、`action`；
- provider 或 scope 等实际由代码维护有限集合的字段。

数据库使用 varchar、JSON 或 OpenAPI 最终序列化为字符串，不改变 Java 内部类型安全要求。枚举在持久化和 API 边界使用项目统一的 `BaseEnum`、TypeHandler 和 JSON 转换机制。

只有租户自定义编码、外部提供方名称、MIME type、审计对象类型等真正开放且无法枚举的标识可以保留 String。保留时必须在字段或所属类型文档中说明开放原因和扩展来源。无法证明开放性的字符串状态字段属于阻塞问题。

### 私有方法

改动文件中的每个私有方法必须归入以下一种类型：

- 独立行为：具有独立、准确、可复用的业务或技术语义；
- 框架边界转换：隔离框架数据形状、生命周期或协议约束；
- 执行步骤：只把完整流程拆成校验、准备、构建、执行、收尾等步骤；
- 无意义包装：只转发、复制字段、绑定常量、调用单个工具方法或改变参数形状。

执行步骤和无意义包装不得保留。应展开回核心流程，或在确实形成独立且可复用的行为后重新命名和设计。

以下形式默认视为高风险：

```java
private String text(String value)
private String requiredText(String value, String message)
private void validate(...)
private void prepare(...)
private void build(...)
private void execute(...)
private void after(...)
private Object convert(...)
private Map<String, Object> nativeHeaders(...)
```

方法短小不是删除理由；只有可以准确命名并独立说明的方法才保留。框架输入转换只有在框架没有更直接的正式 API 时才增加，并通过中文文档注释说明输入来源、转换规则、缺失时的结果、所有者和生效时间。

审查方法名时，先按 `接收者.方法` 阅读，再确认方法名是否用最短自然词表达对象、动作或关系。接收者已经表达对象时，不要批量追加 `For`、`By` 或对象名称；只有关系本身不可省略且名词方法会歧义时才保留关系词。业务方法不得使用裸 `require` 或把 `require` 作为状态和读取动作的统一前缀；可缺失查询、必需读取、状态复核和对象登记分别使用 `find`、`load`、`verify/assert` 和 `add/register/record`。只在底层断言确实表达「输入不满足即失败」且接收者已经明确校验对象时保留 `require`。

禁止通过给步骤型方法补充冗长注释来证明其存在价值。

### 包结构与工具类型

完整执行[代码结构与分包](/standards/03_code-structure)。领域根包只保留直接表达领域的类型，审计、安全、策略、传输、持久化和框架适配进入准确职责子包。业务枚举不得因为 Java 类型相同而集中放入 `enums`。

`Util` 和 `Helper` 可以存在，不能仅根据后缀判断其不合规。完整类型必须满足：

- Util 提供无状态、输入输出明确的通用技术操作；
- Helper 帮助一个明确对象处理有限技术细节或测试准备；
- 类型不拥有业务状态机、事务、Repository 编排和副作用顺序；
- 调用方不需要按步骤串联其函数才能组成完整业务流程；
- 方法没有因为「不知道放哪里」而聚集互不相关的职责。

如果 Util/Helper 实际执行校验、构建、保存、发布等连续业务步骤，应恢复为展开的 Service 流程，或根据它实际完成的独立行为重新命名和设计。Lambda、Stream 和函数式接口本身不是问题，隐藏业务对象、顺序和副作用才是问题。

### 框架使用

Spring、MyBatis、Jackson、Sa-Token、消息框架和其他成熟库的原生扩展点、常量、类型转换、生命周期和错误处理机制优先于自定义实现。

以下情况不符合框架使用要求：

- 使用字符串、反射或手写容器猜测框架生命周期；
- 复制框架内部常量或协议字段但不说明来源；
- 在业务层直接读取 ThreadLocal、RequestContext、消息头或框架 Session；
- 为 HTTP、STOMP、任务等传输方式复制平行的身份、权限或请求模型；
- 单元测试绕过真实框架调用顺序，却把内部占位行为当作正确契约；
- 自定义实现仅重复框架现有的解析、匹配、序列化、缓存或绑定方法。

### 集群成立性

业务逻辑、后台任务、缓存、锁、状态迁移和外部副作用必须在多个应用实例并发执行时仍然成立。单机测试通过不能证明多实例行为正确。

多实例实现必须满足：

- 多个实例同时读取和更新同一数据时，竞争结果由数据库原子条件、乐观锁或分布式协调明确决定；
- 定时任务、消息消费和重试允许重复执行，并具有幂等、抢占、租约、失败释放和恢复语义；
- 本地内存、进程锁、`synchronized`、ThreadLocal 和单机缓存不作为集群一致性边界；
- 数据库提交、缓存失效、消息发布和外部调用之间不存在无法恢复的部分成功；
- 节点宕机、超时、重复投递、乱序和并发重入后，状态仍可收敛；
- 调度迁移到 Quartz 等集群设施后，业务 Service 的原子状态和幂等语义仍可独立成立。

集群竞争、失败恢复和重复执行结果不明确时，实现不符合本规范。「当前只有一个实例」「任务由定时器串行触发」或「后续再做分布式」不构成例外。

### 日志可观测性

业务和基础设施流程除满足[应用日志规范](/standards/08_comments-and-logging)外，还必须具备：

- 可观察的开始、关键决策、状态变化、外部副作用和最终结果；
- 根据事件频率、失败后是否能恢复和最终处理位置选择 INFO、DEBUG、WARN 或 ERROR；
- 能够区分异步受理、事务内写入和真正成功的准确措辞；
- 足以重建执行过程的对象 ID、状态、数量、尝试次数和耗时；
- 仅在最终处理边界记录一次的异常；
- 对密码、Token、签名 URL、完整 Payload 和不必要个人数据的完整排除。

HTTP 访问日志、操作审计和测试输出均不能替代业务阶段日志。新增日志包装层如果只转发 SLF4J 或拼接字段，必须删除。

### 注释、测试和成品一致性

每个文件除满足[注释与成品文档](/standards/08_comments-and-logging)外，还必须满足：

- 接口和接口方法具有有效中文文档注释；
- 私有方法具有有效中文文档注释，无法准确命名和独立说明的方法已经删除；
- 非平凡框架逻辑说明生命周期、顺序、不变量和失败行为；
- 业务方法的中文逻辑注释能够还原完整业务流程；
- JetBrains nullability 注解与所有运行时状态一致；
- 测试覆盖公开契约、真实调用链、失败边界和回归路径；
- 文档、配置、迁移和代码使用同一套当前术语和事实来源。

测试通过、覆盖率较高、格式正确或功能仍在开发都不能降低代码质量要求。验收对象是当前准备提交的完整代码。

### 完成条件

任意不合规项都阻止提交。

- 架构方向、分层、项目语言、核心生命周期或抽象模型错误时必须重写；
- 方向成立但存在可以在原结构内修复的问题时必须完成修改后复验；
- 全部改动文件逐一完成验收、所有问题清零并具有覆盖证据时，Java 工程质量才符合本规范。

单次无法覆盖全部文件时，变更必须拆分到可以完整验收的范围。抽样结果不能代替全文件验收。
