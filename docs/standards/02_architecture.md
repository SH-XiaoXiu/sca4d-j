# 02 功能归属与调用关系

一项数据由哪个模块负责、其他模块通过什么方法使用它、一次 HTTP 请求经过哪几层到达数据库，本页分别说明。目录名称只是这些关系在某个仓库中的具体安排。

## 功能由谁负责

一个功能模块负责一组相互关联的对象、规则和数据。身份模块（IAM）决定 Account 的状态含义，消息模块决定消息何时可以投递；应用从这些模块中选取需要的部分，组成完整业务流程。

以 Account 状态为例：IAM 维护 Account 记录以及 `ACTIVE`、`DISABLED` 的含义。认证模块需要知道账号能否继续登录时，通过 IAM 公开的方法取得结果（例如 `IdentityService.activeAccountById(id)` 这类按状态读取的方法），再决定是否结束自己的 Session。认证模块不读取 Account 表，也不保存一份账号状态。

共同使用的类型只放表达稳定概念、多个模块都需要理解的内容，例如错误码接口和分页结果。只因为两个模块有相似代码，就把其中一个模块的业务类移到共同位置，会让所有模块依赖一个不属于它们的业务类。

## 模块之间怎样调用

- 应用可以调用功能模块公开的方法，功能模块可以依赖共同类型；
- 模块不使用另一个模块的 Mapper、Repository、数据库行类型或内部包；
- 负责某项数据的模块提供能长期保持不变的查询和操作，数据的校验与修改规则因此只有一份；
- 事件可以通知「已经发生的事实」，不能用来绕过另一个模块的公开方法去修改它的数据；
- 不使用反射、全局静态变量或通用工具类建立隐蔽的反向调用。

公开方法可以放在普通类中，也可以放在 Java `interface` 中。需要多个实现、由应用提供实现，或不希望调用方依赖具体实现时，才使用 `interface`。同一模块内只有一个固定实现，直接使用普通类；`Foo` 与 `FooImpl` 一一配对不会让调用关系更清楚。

## HTTP 请求怎样到达数据库

同时涉及 HTTP 和数据库的业务动作，依次经过 Controller、Service、Repository 和 Mapper。每一层只依赖紧邻的下一层：Controller 不依赖 Repository 或 Mapper，Service 不依赖 Mapper。

以停用 Account 为例，各层的方法与它们处理的内容：

| 层 | 方法 | 自己处理 | 不处理 |
| --- | --- | --- | --- |
| Controller | 接收 `PUT` 请求，调用 Service | 路由、参数绑定、权限声明、响应转换 | 事务、状态是否允许变化 |
| Service | `IdentityService.changeAccountStatus(id, status)` | 状态规则、事务、写入后的副作用与日志 | SQL、影响行数 |
| Repository | `IdentityRepository.updateAccountStatus(id, status)`，返回 `boolean` | 把 Mapper 返回的影响行数解释为「已修改」或「目标不存在」；行类型转换；异常转换 | 判断停用是否被业务允许 |
| Mapper | `IdentityMapper.updateAccountStatus(id, status)`，返回 `int` | 一条 SQL：表、列、条件、影响行数 | 状态流转规则 |

每一层把自己的细节留在内部：Mapper 返回 `int`，影响了几行只有 Repository 解释；Repository 返回 `boolean`，Service 不需要知道影响行数，目标不存在时抛出 `BusinessException(IamErrorCode.ACCOUNT_UNAVAILABLE)`；Controller 和 Service 的调用方不需要知道 SQL 写了什么列。

没有数据库访问的流程，不为凑齐调用链创建空的 Repository 和 Mapper。一层的方法如果只是原样转发参数和返回值，就应删除这一层。具体的 Repository、Mapper 写法见 [05 SQL 与持久化](/standards/05_persistence)。

## 数据由谁维护

每张业务表由保存这类事实的模块或应用负责。应用自己的数据放在应用的表中，功能模块不修改别的模块的表。

一个业务动作涉及多个模块时，由拥有该流程的 Service 调用各模块的公开方法，并在方法中写清事务范围、失败后哪些修改保留，以及外部副作用何时发生。

长期保存的数据包括需要恢复、追溯或并发保护的事实。页面临时状态和请求中的中间计算由页面或当前调用持有。派生数据确实需要保存时，要写明由哪段代码更新、何时失效、怎样修复。

## 多实例运行

应用运行多个实例时，Session、任务租约、消息、连接索引、限流额度和失败恢复不能只保存在某个 JVM 的内存中。多个实例同时修改同一个对象时，由数据库的原子条件、版本检查或共享的协调机制决定结果。

定时任务、消息消费和重试可能重复执行。代码要写明：重复执行的结果是否幂等，租约到期后谁接管，节点退出时未完成的工作怎样处理。单实例运行使用同一套规则，不另设一条依赖本地状态的路径。
