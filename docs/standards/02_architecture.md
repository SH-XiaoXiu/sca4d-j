# 02 功能归属与调用关系

一项功能由谁负责、其他功能怎样使用它、产生的数据由谁维护，决定了模块之间的调用关系。目录名称只是这些关系在某个仓库中的具体安排。

## 功能由谁负责

一个功能模块负责一组相互关联的对象、规则和数据。例如，身份功能决定账号与身份的状态含义，消息功能决定消息何时可以投递；应用把需要的功能组合成完整业务流程。模块的划分来自这些职责和独立选择的需要，不来自文件数量。

以账号状态为例，身份功能维护账号记录及「启用」「停用」的含义。认证功能可能需要查询账号能否继续登录，但它不因此拥有账号状态字段。身份功能提供能够回答这一问题的操作，认证功能据返回结果处理自己的会话。两个功能分别维护自己负责的数据与规则。

共同使用的类型应表达多个功能都需要理解、且含义稳定的概念。只因两个模块使用了相似代码，就把某个模块的业务类移入共同约定，会让所有模块承担不属于自己的业务依赖。

## 功能之间怎样调用

应用可以调用功能模块公开的操作，功能模块可以依赖共同约定。共同约定是多个功能都需要理解的类型或操作，其含义不由某个具体功能的数据库结构决定。负责某项数据的模块向其他模块提供能够长期维持的查询或操作；调用方不读取它的 Mapper、Repository、数据库行类型或内部表。数据的校验和修改规则因此仍由同一个所有者维护。

公开操作可以是普通类的方法，也可以是 Java `interface`。接口适合表达需要由不同实现承担、由应用提供实现，或调用方不应依赖具体实现的能力。同一模块中只有固定实现时，普通类通常足够。接口与实现类一一配对不会自动改善调用关系。

用事件通知已经发生的事实是合理的；事件不应让一个模块绕过另一个模块公开的操作去修改其数据。反射、全局静态状态和宽泛工具类也不应承担隐蔽的反向调用。

## HTTP 请求怎样到达数据库

同时涉及 HTTP 和关系数据库的业务动作，通常经过 Controller、Service、Repository 和 Mapper。各层使用的语言不同：

| 位置 | 对调用方表达什么 | 自己处理什么 |
| --- | --- | --- |
| Controller | 一个 HTTP 请求及其响应 | 路由、绑定、权限声明和响应转换 |
| Service | 一个完整业务动作 | 规则、状态变化、事务和副作用顺序 |
| Repository | 对业务动作有意义的数据读取或写入结果 | 聚合加载、范围条件、行模型转换和持久化冲突 |
| Mapper | 一种明确的 SQL 读写结构 | 数据库字段、查询条件、锁和结果映射 |

Controller 不通过 Repository 决定业务状态；Service 不解释 SQL 字段和影响行数；Mapper 不决定业务动作是否允许。Repository 把数据库结果转换成 Service 能理解的读写结果。没有数据库访问的流程，不需要为了凑齐调用链建立空的 Repository 和 Mapper。

从 Mapper 的 SQL 结构，到 Repository 的数据操作，再到 Service 的业务动作，使用的概念逐层改变。每层负责收住自己的实现细节和数据约束，让上一层只依赖公开的操作与结果。[持久化规范](/standards/05_persistence)进一步说明这一抽象梯度与封装梯度。

## 数据由谁维护

每张业务表由保存这类事实的功能模块或应用负责。应用特有的数据保存在应用拥有的表中；功能模块不直接改写其他模块的表。需要跨模块处理一个完整业务动作时，由拥有流程的 Service 调用各模块公开操作，并说明事务、失败和外部副作用的关系。

长期保存的数据包括需要恢复、追溯或并发保护的事实。页面临时状态和请求中的中间计算通常由页面或当前调用持有。派生数据确实需要保存时，负责更新它的代码、失效时机和修复方式也必须明确。

## 多实例运行

应用运行多个实例时，Session、任务租约、消息、连接索引、限流额度和失败恢复不能只保存在某个 JVM 内。多个实例争用同一对象，结果由数据库原子条件、版本检查或共享协调机制决定。

定时任务、消息消费和重试可能重复执行。业务结果因此需要明确幂等、租约到期、节点退出及接管后的处理方式；单实例运行使用同一套规则，不另设一套依赖本地状态的业务路径。
