# 02 架构与边界

Sca4d-J 采用分布式单体架构。一个 App 包含完整业务体系，身份、认证、文件、消息、任务和具体业务在同一业务进程中协作；同一个 App 可以运行一个或多个实例。单实例与集群使用同一套业务代码、数据约束和失败处理。

新增功能先决定数据属于哪个模块，再沿 `Controller -> Service -> Repository -> Mapper` 分配职责；跨模块只调用公开接口。具体的 SQL、并发策略和技术工具见[SQL 与持久化](./05_persistence)、[数据库](./06_database)和[Java 与 Spring](./04_java-and-spring)。

## 顶层目录

| 目录 | 负责内容 | 依赖要求 |
| --- | --- | --- |
| `core/` | 多个模块共同使用、需要长期稳定的接口和基础类型 | 尽量不依赖 Spring，不依赖具体模块或 App |
| `modules/` | IAM、认证、审计、消息、通知、任务、实时通信、IoT 和存储等可选功能 | 依赖 Core 的公开契约，不使用其他模块的内部实现 |
| `apps/` | 选择模块、配置运行环境、提供具体应用的接口和业务流程 | 可以依赖 Core 和模块，Core 与模块不能依赖 App |
| `gateway/` | 可独立部署的 HTTP、SSE、WebSocket 和回调转发入口 | 不读取 App 数据库，不执行业务权限和状态机 |
| `frontends/` | 可替换的管理端示例、前端契约和页面代码 | 不成为后端业务规则的依据 |
| `docs/` | 架构、使用方法、工程规范、参考和需求设计 | 不记录任务进度或临时实现 |

`core` 放长期稳定的共同契约；`modules` 负责可选择的具体功能及其数据；`apps` 负责组合模块和完成应用业务。一个功能是否应该成为独立模块，取决于它是否可以单独选择、替换或运行，而不是文件数量或未来可能的替换。

## 模块边界

模块之间只能通过公开接口协作。一个模块不得直接使用另一个模块的 Repository、Mapper、数据库行类型、内部类或内部包，也不得把另一个模块的表当作自己的 Repository 接口。

新增模块、顶层目录或公共接口前，先确认：

- 现有模块为什么不负责这项功能；
- 这项功能是否需要单独选择、替换或部署；
- 调用方需要依赖哪些长期契约；
- 哪个模块拥有相关数据、自动配置和运行资源；
- 删除或停用该功能后，配置、数据和调用方如何处理。

只有多个长期实现需要共同契约，或者具体应用需要提供实现时，才增加 Java `interface`。单一固定实现不为了形式完整创建接口和 `Impl` 类。

## 依赖方向

后端依赖方向为：

```text
apps -> modules -> core
gateway -> core 或公开应用接口
frontends -> HTTP 契约，不依赖后端实现
```

禁止以下依赖：

- `core` 依赖 `modules` 或 `apps`；
- `modules` 依赖具体 App；
- 一个模块依赖另一个模块的数据库实现；
- `frontends` 以页面判断代替后端权限和业务判断；
- 用事件、反射、静态全局变量或工具类隐藏反向依赖。

模块需要新协作关系时，优先增加表达长期职责的公开接口；如果只是某个流程的临时步骤，应留在拥有该流程的 Service 中。

## 分层职责

后端业务代码按以下方向调用：

```text
Controller -> Service -> Repository -> Mapper
```

| 层级 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| Controller | HTTP 路由、请求绑定、权限声明和响应转换 | 事务、业务状态机、Repository 编排 |
| Service | 完整业务动作、规则、事务、状态变化和外部副作用 | SQL、数据库列、影响行数和 MyBatis 结果结构 |
| Repository | 稳定持久化语义、聚合读写、关系维护和持久化结果 | HTTP 请求、页面动作、业务权限和状态机决定 |
| Mapper | 最小 SQL、条件、锁、字段和数据库结果映射 | 业务动作、业务异常、消息和外部调用 |
| Request | HTTP 或外部协议输入绑定 | 数据库读写和业务流程 |
| View | 对外响应字段、脱敏和展示转换 | 持久化结构和业务状态机 |
| Entity/Row/Result | 数据库结构或 SQL 返回形状 | 对外 API 和页面行为 |

每一层必须完成职责转换并隐藏下层细节。同名、同参数、同返回值的直接转发没有形成新的职责，应删除、合并或转换结果。Service 不直接依赖 Mapper，Controller 不直接依赖 Repository 或 Mapper，Mapper 不决定业务状态机。

## 数据归属

每张表由保存这类数据的模块或 App 负责。模块只维护自己的表、索引和结构片段；具体 App 的资料、订单和业务流程使用 App 自己的表，不追加到公共模块表中。

数据库保存需要长期存在、需要并发保护或无法可靠重建的事实。页面临时状态、可以由稳定数据计算的数量和一次请求中的中间结果默认不写入数据库。需要保存派生结果时，同时设计唯一写入方、更新时机、失效、修复和验证方式。

## 序列化版本与迁移

需要持久化或跨实例恢复的结构，由一个当前版本 Codec 写入，并由版本 Codec 目录按外部版本选择读取策略。`VersionedCodec` 描述一个具体结构版本，`VersionedCodecAdapter` 对外提供统一 Codec；JSON 中的 `formatVersion`、消息信封中的 `envelopeVersion`、审计行的 `payload_version` 和设置行的 `schema_version` 分别选择自己的版本边界，不能混用。

版本变化只在序列化边界提供兼容读取。每个 `Migratable` 只把一个版本转换为下一个版本，`VersionedCodecMigrator` 按完整链路执行多个相邻步骤。正常读取不会自动迁移或写回数据；具体应用、运维命令或一次性任务必须显式调用迁移器，并负责事务、并发条件和保存结果。当前结构统一从 V1 开始，未注册的版本直接失败。

敏感值加密也使用 `SecretCodec`。`SecretCipher` 只负责具体密钥和加密算法，`SettingSecretCodecV1`、`SettingSecretCodecV2` 负责加密用途和密文版本。V1 保留历史读取，V2 负责当前写入；`encryption_context_version` 选择读取 Codec。加密迁移只转换调用方指定的单条密文，不在普通读取、启动同步或数据库扫描中自动执行。

## 跨实例成立性

Session、任务租约、消息、连接索引、锁、限流额度和失败恢复不能依赖某一个 JVM 的本地状态。

多个实例同时读取和更新同一对象时，竞争结果必须由数据库原子条件、乐观锁或分布式协调明确决定。定时任务、消息消费和重试必须允许重复执行，并具有幂等、租约、失败释放和恢复语义。节点宕机、超时、重复投递、乱序和并发重入后，状态仍应能够收敛。

## 新功能的判断

新功能开始前，先根据对象、数据和调用方向决定位置：

1. 如果功能属于已有模块且不需要新的长期协作契约，留在该模块。
2. 如果功能需要独立选择、数据归属或装配条件，再考虑新模块。
3. 如果功能只属于具体应用，放在 `apps/`，不提前扩展 Core 或模块。
4. 如果功能只是传输适配或页面展示，留在对应边界，不把协议细节带入 Service。

新增类型、接口和目录都必须能够说明独立对象或稳定技术职责。只为减少文件长度、复制已有入口或预留猜测中的未来需求而增加结构，不符合本规范。

## 完成条件

- 每个目录、模块和类型都有明确的数据或行为归属；
- 依赖方向符合 `apps -> modules -> core` 和 `Controller -> Service -> Repository -> Mapper`；
- 公开接口表达长期契约，不泄漏数据库、框架或传输细节；
- 具体应用规则没有下沉到公共模块；
- 业务状态、权限、事务、并发和外部副作用有明确负责位置；
- 单实例和多实例执行不会得到两套不同结果；
- 新增结构不是重复入口、临时步骤或无意义包装。
