# 工程验收原则

## 目标

提交后的代码应当稳定、可预测、语义统一，并自然延续当前项目已经形成的语言。

代码质量以长期理解成本、职责清晰度和系统一致性衡量，不以技巧、抽象数量或代码行数衡量。

## 单一语义

一个概念只保留一套业务术语、一套运行时模型和一个事实来源。

以下情况不符合单一语义：

- 同一业务字段的前后端两套计算；
- 同一状态的数据库、缓存和上下文多套来源；
- 同一请求或身份的重复上下文对象；
- 同一路由、配置和默认值的多处维护；
- 同一操作存在多条绕过正常检查的入口；
- 旧名称与新名称同时存在。

负责该数据的字段或 Service 是唯一事实来源，其他模块不重复计算并形成不同结果。

## 稳定核心

核心 API 保持稳定的语义、参数和行为。

业务场景差异通过外围流程表达。只有底层方法执行相同规则并修改相同数据时，才复用该方法。

产品端、管理端、后台任务和外部回调在状态机、权限、副作用、审计或数据访问不同的情况下，使用独立流程，只调用它们确实共用的底层方法。

## 抽象价值

只抽象具有独立、准确、可复用语义的行为和概念，不抽象执行步骤。

类、接口、私有方法、Builder、Factory、Context、Manager、Helper 和包装对象只有形成独立且可复用的语义时才成立。

以下情况通常不构成有效抽象：

- 只转发另一个方法；
- 只包装一到两个基础字段；
- 只完成字段复制；
- 只把完整流程拆成 prepare、build、validate、execute、after 等步骤；
- 只为未来可能出现的需求预留扩展点；
- Mapper 和 Repository 以相同方法一一对应。

无法独立说明语义的抽象不符合验收要求，相关逻辑应保留在完整业务流程中。

## 阅读连续性

核心业务流程保持展开，使阅读者能够从上到下看到完整的校验、决策、状态变化、持久化和副作用。

较长的方法本身不是问题。为了缩短方法而增加跳转、隐藏关键顺序或分散事务语义属于质量下降。

私有方法只有在可以准确命名并独立说明时才保留。

## 项目语言

API、类型、字段、包和路由名称表达业务概念和职责归属。

process、handle、execute、data、info、context、manager、helper、util 等泛化名称只适用于已经形成明确项目含义的概念，不能代替业务名称。

Dto、Command、Result、Payload 等后缀只在对象确实承担对应职责时使用，不能仅靠后缀区分结构相同的对象。

相邻模块已经稳定重复的目录、命名、调用方式和对象结构属于架构语言。新实现应当延续这种可预测性。

## 显式契约

核心 API 优先使用显式参数和清晰类型。

一组参数已经形成稳定业务概念时可以包装；仅为减少参数数量创建的 Context、Options 或 Payload 不符合显式契约要求。

让 Java 类型、泛型、枚举和 JetBrains 注解表达可以在编译期识别的约束。

## 分层职责

每一层使用与其职责相符的语言：

- Controller 表达传输协议、请求绑定、权限声明和响应转换；
- Service 表达业务动作、规则、事务和副作用；
- Repository 表达面向业务的数据访问语义和聚合操作；
- Mapper 表达 SQL 动作、查询条件和数据库结果映射；
- Entity 表达持久化结构；
- View 表达对外响应结构和展示转换。

新增层级必须完成职责转换。Repository 不能只是 Mapper 的同名转发器，Service 不能只是 Repository 的同名转发器。

所有 Java 项目使用 `Controller -> Service -> Repository -> Mapper` 依赖方向。Service 直接依赖 Mapper、Controller 直接依赖 Repository 或 Mapper 均不符合分层要求，不因历史代码、开发阶段或项目规模设置例外。

新增、修改和重命名的文件按完整文件验收。文件中原有的不合规实现同样属于本次验收范围，验收范围不能缩小到新增行。

## 持久化抽象梯度

Service、Repository 和 Mapper 使用不同层级的语言：

- Service 表达业务动作、状态机、权限、事务和副作用；
- Repository 表达持久化读写、聚合加载和持久化结果；
- Mapper 表达最小、可组合、可验证的 SQL 查询和写入形状。

同一个 SQL 形状不因业务动作名称不同而拆成多个 Mapper 方法。Repository 也不因调用方动作名称不同而创建只绑定常量参数的包装方法。

自定义 Mapper 方法数量大于或等于 Repository 公开持久化方法数量属于高风险信号。不存在一一转发、SQL 过度拆分和业务语义下沉，并且每层都完成语义压缩和职责转换时，持久化分层才符合要求。数量本身不作为验收结论。

完整规则见[持久化规范](/standards/persistence)。

## 框架现有接口

优先使用成熟框架和项目已经提供的公共实现入口。

自定义解析、转换、路由匹配、序列化、缓存、消息拓扑、权限通配、对象复制和生命周期管理，只在框架或仓库没有对应标准机制时成立。

框架 API 已经得到所需结果时，删除自定义替代实现。框架 API 无法得到所需结果时，自定义类必须说明新增的输入、输出和失败结果，不再包装一次框架 API。

## 表结构从业务数据开始

建表前先确定数据的拥有模块和生命周期。IAM 保存 Account、Principal、Role 及其关系；Auth 保存 Credential 和 Session 控制数据；IoT 保存 Product、ThingModel、Device 和下行状态。具体 App 的资料、订单和业务流程使用 App 自己的表，不追加到公共模块表中。

Account 与 Principal、Principal 与 Role、Role 与 Operation 使用关系表，便于独立修改和查询授权。通用主体引用使用稳定标识，员工、客户等业务资料由对应模块保存；不把页面中的临时角色写进公共表结构。

页面选中项、展示标签、临时步骤和能够用已有字段直接查出的计数不因为需求文档中出现了名词就建表或加列。性能要求需要保存派生结果时，同时定义唯一写入方、更新时机、并发条件和重建方法。

有限状态、单位、范围和可空性在 Java 类型与数据库约束中使用同一含义。不用字段名、默认值或重复表结构隐藏 Java 类型已经可以明确表达的业务限制。

## 多实现决策

同一操作存在多个长期使用的实现时，使用接口、策略或项目已有的扩展机制集中分派。

provider、类型或模式判断集中在一个分派位置。只有一个固定实现且没有稳定扩展语义时，不增加只为形式完整而存在的接口。

## 变更一致性

功能完成意味着相关表面使用同一套最终契约：

- 源码；
- API；
- 配置；
- 数据库迁移；
- 测试；
- 文档；
- 前端或其他调用方；
- 日志、事件和通知。

重命名和边界调整完成后，源码、配置、测试和文档中不再保留旧名称、旧路由、旧配置项、重复默认值和过期说明。

## 证据优先

故障修复以实际失败路径和真实界面为验收对象。错误信息、截图、日志和 SQL 结果用于确定发生问题的调用与数据。

根因必须由日志、断点、请求记录、数据库数据、构建产物或运行时调用链证明，不能仅根据相邻代码推测。

相邻但未发生问题的页面或接口发生变化，不能作为原故障已经修复的验收证据。

## 范围纪律

变更范围包含当前功能及其必要影响面，不包含与目标无关的历史代码整理。

范围外技术债只有在直接导致当前功能错误、无法验证或破坏已确认契约时，才进入本次变更。

工作树中与当前变更无关的已有修改保持原状，不回滚、不覆盖，也不进入本次提交。

## 完成条件

新增或修改的类、接口、方法和字段必须同时满足：

1. 表达可以独立说明的业务概念或技术职责；
2. 位于负责该职责的模块和分层；
3. 没有复制项目中已经存在的概念或公共实现入口；
4. 抽取的方法或类型表达独立行为，而不是业务流程中的执行步骤；
5. 没有重复实现框架或项目现有机制；
6. 所有调用方、测试、配置和文档使用同一套当前契约。

任一条件不成立时，变更不符合本规范。

## 修改范围

### 只修改相关文件

变更范围只包含目标功能及其必要依赖。工作树中的无关改动保持原状，不格式化、不移动，也不进入当前变更。

### 需要一起修改的内容

目标功能的直接调用位置、测试、配置、数据库迁移、前端和文档属于同一变更范围。与当前功能无关的代码整理不在范围内。

### 删除旧实现

新语义落地后，范围内不再保留旧字段、旧路由、旧类型、兼容转换和无调用代码。当前源码不能同时保留两套语义。

### 不主动重构

不影响目标正确性的架构调整不进入当前变更。业务变更不能附带与目标无关的新抽象、业务数据结构调整或设计模式。

### 同一文件中的问题

同一文件中导致编译失败或直接安全问题的现有代码属于必要影响面。会改变其他业务功能的处理必须形成独立范围和验收条件。

### 验收记录

验收记录包含实际变更、验证命令及结果、未执行项和原因。已完成状态必须对应直接证据，不能使用“应该”或“大概”代替结果。

## 可预测的工程结构

### 适用范围

本规范适用于新增业务模块、公共功能、目录、API、数据库对象和管理端页面。它补充[核心编码规则](/standards/principles)，用于判断新实现是否保持项目整体一致。

### 优雅就是可预测

目录、类型、方法和调用方向必须让熟悉项目的开发者能够预测。新增功能沿用已通过验证的同类实现位置、命名和调用方式。

正例：新的租户资源沿用 Request、Service、Repository、Mapper、View 和权限 Policy 的现有结构。

反例：为了减少文件数量，把 Controller、SQL 和响应拼装放进同一个 Service。

### 架构最终表现为样板

经过验证的复杂决定必须落实为可重复的代码形状、配置位置和测试方法。文档不能只说明设计意图而不给出实现位置和验收方式。

重复出现的业务功能必须具有固定的：

- 代码包位置；
- 类型命名规则；
- 调用入口层级；
- 数据范围应用层级；
- 行为验证方式。

### 每一次重复都是设计决策

稳定重复的目录、API、数据库字段和调用顺序构成项目语言。不得仅为减少表面重复而引入通用 Map、动态路由、反射分派或无业务语义的中间层。

重复的目录和调用形状可以作为项目样板保留。重复代码只有具有独立、准确、可复用的业务或技术语义时才允许提取。

### 框架应当隐形

业务代码应直接使用 Controller、Service、Repository、Entity 和框架标准扩展点。自定义框架层只有在补充现有框架缺失的稳定语义时才允许存在。

禁止新增以下包装：

- 只转发 Spring Bean 调用的 Manager 或 Helper；
- 只把 Mapper 或动态 SQL 包装起来、却不转换任何持久化结果的通用查询器；
- 让业务代码依赖容器细节的全局 Service Locator；
- 重新实现事务、校验、配置绑定或生命周期的自定义机制。

### 架构是团队记忆

已经解决过的分层、并发、权限、配置和运行问题必须固化到代码样板、规范和测试中。新实现不得绕过现有入口重新解决同一问题。

现有做法不适用时，新结构必须明确记录：

1. 当前样板无法表达的具体语义；
2. 受影响的调用者和数据；
3. 新结构如何用于后续同类功能；
4. 迁移、测试和文档范围。

### 工程成功的标准

新成员不需要了解全部设计历史，也应能根据现有代码和文档写出位置、命名、边界和质量一致的功能。合格的工程结构同时满足：

- 新文件位置可以从工程结构预测；
- 同类 API 使用相同参数和失败语义；
- 不存在第二套请求态、权限、消息、文件或配置入口；
- 主要流程不需要频繁跨文件跳转才能读懂；
- 测试覆盖多实例、失败和恢复行为；
- 文档包含当前主要定义和准确参考。

任一条件不成立时，编译或单个测试通过不能作为工程结构合格的依据。

## 认证与权限失败

认证、权限、数据范围、签名、配置校验或关键依赖异常时，拒绝当前操作。解析失败、空集合、未知枚举或服务异常不能转换成全权限、全部范围或默认成功。

旧实现废弃后同步删除调用方、测试和配置中的旧入口。存在明确外部消费者时，兼容方案必须说明迁移窗口和删除条件。
