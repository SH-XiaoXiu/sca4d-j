# 文档规范

文档优先保证准确、清晰、可使用和易查找，再考虑覆盖范围与文字修饰。写作前确认读者、任务和已有入口，并阅读直接相关的 README、源码、测试、配置、示例及构建文件。

Java 类型、方法、参数、返回值和异常写在源码 Javadoc 中。Markdown 解释架构、操作方法、HTTP 与运行配置、工程规则和业务需求。

## 页面责任

| 位置 | 回答的问题 |
|---|---|
| 首页与 `home/` | Sca4d-J 是什么，核心对象如何协作 |
| `tutorials/` | 按什么顺序完成一个可验收的任务 |
| `standards/` | 修改和评审代码必须遵守什么 |
| `reference/` | HTTP、运行配置和 Java API 的准确契约 |
| `requirements/` | 具体 App 的用户、场景、规则与实现设计 |
| `ai-collaboration/` | 开发者怎样准备任务、确认计划和验收修改 |

一项行为、配置、协议或规则只由一个页面完整说明。教程只保留完成任务需要的输入；概念页解释关系和边界；参考页集中列出契约；项目规范规定实现要求。其他页面用链接引用。

## 内容来源

先判断页面说明设计目标还是可执行的当前行为。概念页和项目规范可以说明已确认的最终职责；教程、HTTP 参考和运行配置必须与当前源码、配置、迁移、测试或运行结果一致。

核对顺序：

1. 本次任务中明确确认的目标和取舍；
2. 已经生效的项目规则和概念文档；
3. 源码、测试、配置、数据库迁移和实际运行结果；
4. Git 历史和只读的旧 Gateway 参考。

外部框架和协议优先链接官方文档。只写 Sca4d-J 做出的选择、配置和限制，不复制 Vben、Spring、PostgreSQL 或 Gradle 的通用教程。

## 教程

一篇教程完成一个可以独立验收的任务。开头直接说明完成后的结果，正文按真实操作顺序展开，到读者能确认结果时结束。

标题直接使用当前动作，例如“注册设置定义”“提交 `If-Match`”“确认命令已应答”。前置条件放在第一次需要它的位置，验证放在关键操作之后。只有实际存在且常见的失败才写处理方法。

不为所有教程复制同一组“结果、前提、操作、验证、故障、参考”标题。不写内容提要、章节回顾、形式化总结和没有实际条件的建议。

文档按读者任务组织，不照着源码目录逐个生成页面。介绍说明用途和位置，概念解释影响使用的对象与关系，教程完成操作，示例展示真实案例，参考供精确查询。这些职责可以作为已有页面中的内容安排，不要求为每个字段、类或话题增加一页。

## 概念与示例

核心概念需要解释到读者能正确使用的程度。根据主题说明它是什么、为什么需要、与哪些对象关联以及本项目怎样实现；这些是写作时的判断问题，不是固定标题。简单概念用两三段即可，复杂关系再展开。背景、历史、优缺点、FAQ 和展望只有在能帮助理解当前项目时才写。

例如 Property 是设备属性，可以用温度或电量说明；不要将它重新命名为“状态描述单元”。描述 Device 包含 Property 即可，不据此创造源码中没有的“设备能力绑定模型”。正式术语依次采用项目已有名称、依赖或协议官方术语、行业通用术语。首次需要解释时说明含义，后文保持同一名称。

示例优先取自项目源码、测试、官方示例、真实配置和已确认使用场景。人工构造的最小示例必须说明需要由应用定义的类型，并核对调用的 API、参数和结果。不能根据其他项目或模型常识补出本项目不存在的接口、模块、生命周期和系统行为。

引用代码时解释前置条件、关键选择和失败结果，不逐行翻译语法。参考页集中列字段、配置、协议和错误码，概念背景通过链接阅读。介绍、教程、示例与参考相互链接，不为搜索关键词或形式完整创建重复页面。

## 正文

每句话写清具体对象、条件、动作和结果。可以直接定位的类、方法、字段、注解、配置键、路由和协议字面量使用准确标识符。不先创造一个中文名称再用括号补标识符。

不使用“赋能”“抓手”“收口”“承载”“治理”“闭环”“口径”“打通链路”“完成适配”“提供能力”等抽象说法代替代码和结果。不使用大量“不是……而是……”构造假对比。存在真实取舍时，直接写选择、原因和结果。

三个以上对象协作、存在状态分支或数据归属容易混淆时，优先用 Mermaid 表达关系。图中使用真实模块、类型、路由、配置键或数据项。删除图后不影响理解时省略图，不把一句简单说明改画成几个方框。

## 变更位置

- 项目定位、架构或核心关系变化：检查首页和 `home/`。
- 读者完成某项操作的步骤变化：检查对应教程。
- 工程约束、审查或验收方式变化：检查项目规范。
- HTTP 路由、请求、响应、权限或配置键变化：检查 `reference/`。
- Java 类型、方法、参数、返回值或异常变化：先更新源码 Javadoc。
- App 用户、场景、业务规则或验收结果变化：检查 `requirements/`。

实现变化没有影响读者理解时，不制造无意义的文档改动。

## 页面生命周期

新增页面前先确认它是一个可独立完成的任务、长期存在的概念或集中维护的参考。内容能够进入已有页面时，不增加导航入口。禁止创建只有标题、TODO 或“待补充”的占位页。

移动或删除页面时，先把仍有效的内容并入唯一责任页，再修改导航、入站链接和相关正文。Git 保存历史，不为已删除的内容长期保留空转发页。

## 检查

每次修改都完整重读改动页，检查相邻入口、链接和 `git diff --check`。修改导航、内部链接、VitePress 配置或文档生成输入时，运行完整文档站构建。普通正文修改不启动 Java 编译或业务测试。

Javadoc 链接以 `build/docs/site/javadoc/` 中的实际文件为准。VitePress 构建成功只能证明 Markdown 站可以生成，不能代替 Javadoc 生成检查。

## 核对依据

| 需要说明的内容 | 至少核对 |
|---|---|
| Java 类型和公开方法 | 声明、实现、直接调用方、现有测试和 Javadoc |
| 状态变化、事务、并发与失败 | 实现、异常处理、持久化写入、锁和事务提交位置 |
| HTTP 接口 | Controller、请求与响应类型、异常映射、OpenAPI 或实际响应 |
| 数据库 | Flyway、Java 类型、Repository、Mapper 和 SQL |
| 配置 | `@ConfigurationProperties`、默认值、YAML 或环境示例、装配和启动检查 |
| 外部服务 | 调用代码、超时或重试配置、失败处理和健康检查 |
| 工程规则 | 已确认的项目规则、现行构建入口和同类源码 |

功能设计写任务发起人已经确认的最终职责和关系。准确行为、配置和失败结果写当前实现能够证明的内容。两者冲突且会让读者得到不同业务结论时，说明冲突页面、代码位置和两种结果，请任务发起人决定。

## 外部材料

概念页可以引用标准发布方规范和第三方维护者官方文档，但必须说明它们与 Sca4d-J 的关系：

| 材料 | 可以说明 | 不能说明 |
|---|---|---|
| 标准发布方的正式规范 | 标准名称、术语、交换格式和模型 | Sca4d-J 是否实现该标准 |
| 第三方维护者的官方文档 | 组件功能、配置和使用模型 | Sca4d-J 是否选择或装配该组件 |
| Sca4d-J 源码、配置、迁移、测试和已确认设计 | 当前代码怎样运行以及已确认职责 | 外部标准或组件的完整语义 |

历史只在能解释当前选择时写。必须分别说明过去做法和当前代码，不能用旧目录或旧依赖推断现行行为。

## 术语、代码和链接

使用读者能理解的中文说明概念，存在准确类型名时直接写类型名。Java 类型名和项目概念名使用普通文字或普通链接；方法调用、字段、枚举值、注解、配置键、路由、路径和协议字面量使用行内代码。

中文正文沿用本项目的弯引号“”。代码标识符、JSON、配置、路由和协议字面量保持原文；不因排版检查建议改变大小写。中文段落一段一行，代码、表格、引用和 Markdown 容器保留必要换行。

Java 类型链接使用标准 Javadoc 地址。例如：

```md
[Session](/javadoc/core/sca4dj-core-api/com/sca4d/core/api/authentication/Session.html)
```

每个链接必须指向能够核对当前结论的页面或章节。目录页只能作为阅读入口，不能代替具体行为、配置或规则页面。

## 图和关系说明

每张图只回答一个问题，根据关系选择图形：

| 内容 | 图形 |
|---|---|
| 步骤、判断、分支或数据流 | `flowchart` |
| 请求、调用与消息先后 | `sequenceDiagram` |
| 类型、继承与组合 | `classDiagram` |
| 生命周期和状态转换 | `stateDiagram-v2` |
| 数据库实体与关系 | `erDiagram` |
| 系统组件、依赖与边界 | 架构图或 `flowchart` |

一张图通常保留 3 至 8 个核心节点，超过约 10 个时先删除无关节点、把细节移入正文或按问题拆图。节点使用实际模块、类型、方法、路由或数据项，名称简短，不放完整长句。不要用普通流程图代替需要表达状态的状态图，也不要为画图生造 Layer、Context 或 Capability。

正文说明定义、原因和规则，图说明关系、顺序、分支与变化。先交代需要理解的问题，图后解释关键条件、失败位置和数据变化，不在图前后重复同一段流程。图中的关系和箭头与代码一样需要源码、测试、配置或已确认设计支持。

优先使用站点支持的 Mermaid；其他发布载体先确认渲染支持。最终检查图是否增加了文字之外的信息，读者是否能从页面完成常见任务并找到准确参考。

图不是证据。不能准确命名的节点必须先回到源码或确认设计，不能用“平台”“中心”“统一入口”等模糊方框代替未确定的责任。

## 应用与公共功能

只修改应用业务时，更新对应教程、应用 HTTP 参考、运行配置和需求设计，不复制公共模块说明。公共功能变化时，检查概念、操作步骤、工程规则及源码 Javadoc。导航或目录变化同时更新 VitePress、docs/AGENTS.md 和构建目标。删除可选功能后检查是否还存在指向它的配置、教程和导航。

移动或合并前列出仍有效的规则、条件、例外、失败结果、代码块及链接，逐项确认新位置。文件名使用小写英文和连字符，标题使用读者查找的对象或动作。任务进度、分支、提交和临时 TODO 只写入任务发起人指定的记录。
