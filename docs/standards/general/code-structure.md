# 代码结构与分包

## 目标

包名首先表达业务领域和稳定职责，其次才表达技术层。熟悉项目的开发者应能根据一个类型的名称预测它属于哪个包，也能根据包名预测其中允许出现哪些类型。

分包不是让目录看起来整齐。每增加一层包，阅读者都会增加一次定位和跳转成本，因此新包必须带来明确分类价值。

## 领域根包

领域根包只放能够直接表达该领域的核心词汇、稳定业务类型和公共能力。

例如 IAM 的类型按稳定子域表达归属：

```text
com.sca4d.iam.tenant.TenantType
com.sca4d.iam.tenant.TenantStatus
com.sca4d.iam.account.AccountService
com.sca4d.iam.subject.SubjectLock
```

`TenantType` 的完整含义已经由 `iam.tenant.TenantType` 表达。放入 `iam.tenant.enums.TenantType` 只增加“它是 Java enum”这一实现分类，没有增加业务信息，因此不成立。

领域根包不是无条件的扁平目录。一个类型虽然服务于该领域，但如果名称主要表达传输、持久化、展示、框架或横切职责，就不应放在根包。

## 职责子包

以下内容通常需要进入明确子包：

- `request`：HTTP 或其他入口的输入绑定；
- `view`：对外响应与展示转换；
- `repository`：稳定持久化能力和聚合加载；
- `service`：接口已有稳定根包位置时的实现类；
- `audit`：该领域的审计 operation、Payload 和贡献者；
- `security`：安全协议、密钥处理和安全框架接入；
- `policy`：明确的权限或业务策略；
- `storage`：文件、对象或其他存储实现；
- `realtime`：实时消息转换和发布；
- `codec`：协议编码与解码；
- `quartz`：Quartz 生命周期和 Job 适配。

子包名称必须说明其中类型共同承担的职责。只有一个类且看不到后续同类职责时，先判断该类是否直接属于领域根包，不为了包裹单个文件机械建目录。

审计、安全、策略等横切内容不能散落在领域根包，因为它们描述的是“如何约束或观察该领域”，不是该领域对象本身。

## 禁止按 Java 类型收纳

禁止默认创建以下包：

```text
enums/
dto/
vo/
bo/
po/
impl/
interfaces/
classes/
model/
result/
```

这些名称只说明 Java 形式，不能说明业务归属和职责。业务枚举放回领域根包；Request、View 按真实传输边界归类；查询行投影进入所属子域的 `repository`，一次操作返回值使用能说明业务语义的类型名和包；实现类放入其实际业务或技术职责所属的位置。

例外必须是该 Java 形式本身已经成为技术能力。例如 `common.enums` 保存 `BaseEnum`、Codec 和 TypeHandler，解决的是所有枚举的转换机制，不是把各领域业务枚举集中收纳。

## Util 与 Helper

`Util` 和 `Helper` 可以存在，但类型必须真实承担对应职责，不能仅用后缀逃避领域命名。

### Util 成立的条件

Util 适合无状态、输入输出明确、可独立验证的通用技术操作，例如文本编码、时间格式转换、摘要计算或受控的启动检查。通常具有以下特征：

- 不保存业务状态；
- 不决定业务动作是否允许；
- 不开启事务，不编排 Repository；
- 不选择消息、通知和审计副作用；
- 相同输入产生可预测结果；
- 调用方不需要按隐藏顺序调用多个方法才能得到正确业务结果。

### Helper 成立的条件

Helper 只帮助一个明确对象处理有限技术细节、协议适配或测试准备。名称必须说明帮助谁、处理什么，例如测试夹具的请求准备或某个协议的字段装配。

Helper 可以持有完成该技术协助所需的依赖，但不能成为另一个 Service：

- 不拥有业务状态机；
- 不组合多个业务步骤形成主流程；
- 不因为“不知道放哪里”而接收互不相关的方法；
- 不让 Controller 或 Service 按 `validate/prepare/build/execute/finish` 顺序调用它。

### 禁止伪装的函数集合

业务流程不能被拆成一组 Util/Helper 函数，再由调用方手工串联：

```java
OrderHelper.validate(request);
OrderHelper.prepare(order);
OrderHelper.save(order);
OrderHelper.publish(order);
```

这些方法共同表达的是完整订单流程，应由业务 Service 连续展示。把流程改写成静态函数集合没有形成新能力，只是把面向业务的代码退化为步骤编程。

Java Lambda、Stream 和函数式接口本身不受禁止。只有当它们隐藏业务对象、状态变化、顺序、事务或副作用时才不合规。

不建立全局 `utils` 或 `helpers` 杂物包。多个工具形成明确技术类别时，按 `text`、`time`、`logging`、`serialization` 等真实能力组织；无法形成类别时，将类型放到它实际服务的模块。

## 层级和嵌套

包层级保持最浅可读结构。增加第二层、第三层子包前必须说明：

1. 上一层同时存在至少两个不同职责；
2. 新层能够排除不属于它的类型；
3. 调用者可以根据名称预测类型位置；
4. 新层不是为了隐藏文件数量。

例如 `common.messaging.outbox` 成立，因为 Outbox 具有独立的持久化、抢占、重试和投递职责。`iam.enums.status` 不成立，因为它连续按 Java 类型和字段类型分类，没有业务价值。

## 既有工程层

项目已经确认以下全局位置：

- Controller 位于 `com.sca4d.controllers`；
- Entity 位于 `com.sca4d.entity`；
- Mapper 位于 `com.sca4d.mapper`；
- 配置装配位于 `com.sca4d.config`。

这些位置是当前项目的持久化和入口架构，不因为领域根包规则在单次功能中搬迁。领域内部仍按本规范组织业务类型、Repository、Request、View 和横切职责。

## 参考已经通过测试的代码

新增功能时参考仓库中已经通过测试的写法，包括 Request 调用 Service、Repository 使用 AccessCriteria、事务提交后发送消息以及管理端处理 409。不要只根据类名猜测调用方式。

## 触及即整改

新增、修改、重命名和移动的类型必须检查完整包归属。改动代码不得继续新增对不合规类型收纳包的依赖；必要时在同一变更中移动定义并更新全部 import、反射名称、配置、测试和文档。

未触及历史包不做无关全库迁移。只要移动已经成为当前功能正确分包的必要条件，就不能以影响消费者较多为由保留双路径或兼容壳。

## 完成条件

新增、修改、重命名和移动的类型必须同时满足：

1. 包名和类型名能够说明业务对象与职责；
2. 领域职责与审计、安全、策略、传输、持久化等支持职责位于对应位置；
3. 子包表达稳定概念，不按 Java 语法形式收纳文件；
4. Util 和 Helper 不包含业务流程或被拆出的执行步骤；
5. 同类代码使用相同位置，没有形成第二套目录语言。

任一条件不成立时，类型位置不符合本规范。
