# 工程哲学与核心编码规则

## 目标

本项目不以最快增加功能为目标，而是在持续迭代中保持系统稳定、可维护和一致。代码是否优雅，不由行数、类数量、设计模式或抽象层级决定，而由五个月、五年以后是否仍能准确理解和安全修改决定。

下面十二项原则用于设计、实现和评审。它们不是口号；发生冲突时必须回到真实业务对象、调用关系、数据变化和失败结果，选择让系统更可预测的结构。

## 一、稳定核心，丰富边缘

核心能力应长期保持语义、参数和行为稳定。业务场景差异发生在外围流程，不通过不断增加布尔开关、可空参数和分支污染核心 API。

例如 `createOrder(...)` 表达稳定的创建能力。人工创建、VIP 创建和批量创建具有不同权限、状态机或副作用时，应由外围 API 组织这些差异，再调用真正共享的底层能力。

不能因为多个场景最终都写同一张表，就把全部场景塞进一个包含十几个选项的核心方法。是否复用取决于业务规则和失败结果是否相同，而不是最后一条 SQL 是否相同。

长期核心和业务变体必须具有明确边界，业务变体不能改变核心契约。

## 二、抽象的是能力，不是步骤

抽象必须形成可以独立命名、独立测试并在调用方语言中成立的能力，例如 `QRCodeGenerator`、`PermissionEvaluator`、`SqlCompiler`。

`prepareOrder`、`validateOrder`、`executeOrder`、`afterCreateOrder` 只是在描述执行顺序。把它们提取成 private 方法不会产生新概念，只会迫使阅读者来回跳转。

重复几行代码也不自动意味着应该抽象。只有两段代码需要相同输入、产生相同结果，并会因为同一业务原因共同变化时，提取才有价值。

## 三、核心逻辑保持展开

一个方法可以有几十甚至上百行，只要它始终表达一个完整业务流程，并能从上到下看到校验、决策、状态变化、持久化和副作用。

较长方法需要清楚的业务顺序和必要注释，而不是通过步骤型方法隐藏顺序。事务中哪些写入共同回滚、事件何时发布、失败后保留什么数据，都应在主流程中连续可见。

当一段逻辑确实形成独立算法、框架回调或可复用业务判断时才提取。提取后必须能准确说明输入、输出、所有权和失败行为。

## 四、API 是项目语言

API 不是实现细节，而是团队描述业务的句子。方法名必须表达业务动作，例如 `publishAnnouncement`、`disableAccount`、`claimForDispatch`。

禁止使用 `process`、`handle`、`execute`、`doCreate` 等泛化动词掩盖真实行为。一个方法如果无法用业务语言命名，通常意味着职责还没有确定。

不同层使用不同语言：Service 表达业务动作，Repository 表达持久化能力，Mapper 表达 SQL 形状。不能因为调用链相邻，就让三层使用同名、同参数、同返回值的方法。

## 五、显式优于隐藏

核心 API 的必要输入应显式出现在签名中。只有一组参数已经形成稳定业务概念时才包装为对象，不能只因为参数较多就创建 Context、Options 或 Payload。

业务参数不得藏在全局变量、ThreadLocal、Servlet Request 或通用 Map 中。请求身份只能从统一 CurrentRequest 读取；真正由调用方决定的业务对象和动作仍应显式传入。

显式也适用于失败：找不到、无权限、冲突、外部失败和内部异常不能都用 `null` 或 `false` 表达。

## 六、名称必须表达真实概念

优先使用 Order、Payment、Permission、InstallationTask 等业务名称。Request、View、Result、Entity 等后缀只有在类型确实承担对应边界职责时才使用。

DTO、VO、BO、PO、Data、Info、Context、Manager 等泛化名称不能代替业务命名。`Util` 和 `Helper` 可以存在，但必须真的是无状态通用操作或有限技术协助，不能承载状态机、事务、数据库流程和副作用编排。

名称判断不是维护禁用词表。关键问题是：只看类型名和包名，调用者能否预测它处理哪个对象、做什么、不会做什么。

## 七、数据库只保存稳定事实

数据库保存需要长期存在、需要并发保护或无法可靠重建的数据，不保存页面临时状态、易变角色投影和可以通过明确条件计算的重复结果。

通用主体引用优先使用 `principal_id`，员工、客户、商户等业务角色通过类型和扩展表表达。不能因为当前只有一种角色，就把角色名称固化到所有通用表结构中。

派生计数和状态只有在性能、一致性和恢复要求证明必须持久化时才保存，并同时设计更新、失效、修复和验证机制。

## 八、业务约束交给类型系统

数据库负责存储、唯一性、非空和索引等稳定完整性。Java 类型、泛型、枚举和 nullability 负责表达业务允许的对象和有限状态。

系统定义的 status、type、mode、operation 不得降级为 String。数据库列是 varchar、OpenAPI 输出是字符串，都不改变 Java 内部类型安全要求。

真正开放的外部编码可以使用 String，但必须说明扩展来源以及为什么无法枚举。无法证明开放性时，按有限状态处理。

## 九、删除优于兼容

本项目不是公共 SDK。旧逻辑废弃后应直接删除，版本历史由 Git 保存，源码只描述当前有效行为。

重命名和契约调整必须同步更新调用方、测试、配置和文档。禁止保留 deprecated 壳、双路由、双字段和无期限转换，让维护者继续判断哪一条路径才是当前事实。

兼容只有在存在明确外部消费者、迁移窗口和删除条件时成立，不能把“可能有人使用”当作长期保留理由。

## 十、新增复杂度必须产生价值

新增类、接口、Builder、Factory、Context、Manager、Helper、Util、private 方法和包层级必须产生可以独立说明的稳定概念或能力。

如果新增结构只是转发调用、复制字段、绑定常量、缩短方法或为未来猜测预留扩展点，就没有产生价值，应删除并展开。

复杂度可以成立，例如日志来源转换器集中生成模块与类名、Repository 隐藏乐观锁影响行数、Codec 隔离外部协议。这些结构都消除了调用方必须重复理解的真实细节。

## 十一、保持阅读连续性

代码应尽可能从上到下一次读完。阅读者不应为了理解一个流程持续执行“跳转、返回、再跳转”。

核心状态变化、事务范围和副作用顺序留在主流程。辅助能力可以跳转，但跳转后应看到一个完整、准确、边界清楚的概念，而不是又一层转发。

认知复杂度比代码行数重要。减少行数却增加调用深度、隐式回调和跨层猜测，不是简化。

## 十二、整个项目像一个人编写

所有模块保持一致命名、抽象、API 风格、目录结构、日志格式和失败处理。新人应能根据一个已经完成的模块预测新功能放在哪里、叫什么、如何扩展和怎样验证。

一致不等于把所有差异强塞进一个通用框架。业务不同可以使用独立流程，但相同层级、相同设施和相同失败语义应使用同一种表达。

现有模式不适用时，具体业务差异、新结构和受影响的同类消费者必须同步写入公共规范。单个模块不能建立未被项目定义的第二套做法。

## 完成条件

完成的实现同时满足：

1. 核心 API 不包含只服务于单个业务变体的分支；
2. 新增抽象具有独立的业务或技术意义；
3. 完整流程没有被拆成一组步骤函数；
4. 必要输入、状态和失败结果保持显式；
5. 名称、包和 API 延续项目语言；
6. 数据库只保存需要长期维护的事实；
7. 类型系统表达有限状态和业务约束；
8. 旧实现和无效兼容入口已经删除；
9. 新增复杂度消除了真实的重复理解成本；
10. 主要流程可以连续阅读；
11. 同类功能的位置和写法可以从现有项目预测；
12. 日志、测试、配置和文档使用同一套当前事实。

任一条件不成立时，实现未达到完成标准。编译通过不能替代这些条件。
