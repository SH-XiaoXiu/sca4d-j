# 13 文档规范

文档开头用两三句话说明核心概念、适用任务和使用入口，让开发者能够决定下一步做什么。正文再展开必要条件、操作、示例与失败处理；准确性优先，不为缩短篇幅删掉限制，也不写任务进度和作者的工作过程。

## 页面责任

| 位置 | 回答的问题 |
| --- | --- |
| 首页与 `home/` | Sca4d-J 是什么，核心对象怎样协作 |
| `tutorials/` | 怎样按顺序完成一项可以验收的操作 |
| `standards/` | 修改、评审和维护代码必须遵守什么 |
| `reference/` | HTTP、运行配置和 Java API 的准确契约是什么 |
| `requirements/` | 具体 App 的用户、场景、规则和实现设计是什么 |

一项行为、配置、协议或规则只由一个页面完整说明。其他页面使用链接引用，不复制同一段完整内容。Java 类型、方法、参数、返回值和异常由源码 Javadoc 负责；Markdown 解释架构、操作、HTTP、运行配置、工程规则和业务需求。任务执行规则单独维护，不属于工程规范正文。

## 内容来源

先判断页面写的是设计目标还是当前可执行行为：

- 概念页和工程规范可以说明已经确认的最终职责；
- 教程、HTTP 参考和运行配置必须与当前源码、配置、迁移、测试或运行结果一致；
- Java API 的签名、继承关系、参数、返回值和异常必须来自源码 Javadoc；
- 外部框架和协议只引用正式发布方或维护者的资料，并明确区分外部模型和 Sca4d-J 的选择。

核对内容时优先查看已经确认的目标、现行规则、源码、调用方、配置、迁移、测试和实际运行结果。Git 历史只用于理解原因，不用旧目录或旧实现推断当前行为。

设计目标和当前实现存在差距时，正式文档仍然说明最终职责；实现差距由维护记录单独说明。两者冲突且会使读者得到不同业务结论时，先解决冲突再更新页面。

## 工程规范的写法

工程规范回答「选择是什么、为什么这样选择、怎样判断是否符合、失败时会发生什么」。规则应落到对象、条件、动作和结果，不只写抽象价值判断。

例如，不写「统一管理数据访问」，而写「Service 负责业务动作和事务，Repository 隐藏 Mapper、SQL 字段和影响行数，Mapper 只表达 SQL 形状」。不写「加强稳定性」，而写「任务允许重复执行，数据库条件、幂等键或租约决定重复执行的结果」。

一个页面可以合并多个紧密相关的规则，但不要为了形式完整建立一页一个类或一页一个字段。页面无法独立说明概念、操作或判断时，应并入已有责任页。

## 概念与示例

核心概念首次出现时，先写它处理的对象和用途，再用一个具体例子说明怎么用。不要先列出一串类型名、包名和实现组件，要求读者读完整页后自行推导关系。长篇参考可以保留完整字段表，但入口必须能按任务定位到具体章节。

核心概念说明对象是什么、为什么需要、与哪些对象关联、数据归谁以及失败在哪里。简单概念用几段话说明，只有关系复杂或状态分支容易误解时才展开图和表。

示例优先取自源码、测试、正式配置和已确认场景。人工构造的最小示例必须说明哪些类型或值需要由具体应用定义，并核对 API、参数和结果。不能根据其他项目或常识补出 Sca4d-J 没有的接口、模块和生命周期。

引用代码时解释前置条件、关键选择和失败结果，不逐行翻译 Java 或 TypeScript 语法。参考页集中列出字段、配置、协议和错误码，概念页通过链接说明背景和关系。

## 正文表达

每句话写清具体对象、条件、动作和结果。存在可以直接定位的类、方法、字段、注解、配置键、路由或协议字面量时，直接使用准确标识符，不先创造一个中文别名再补代码名称。

不使用抽象套话代替实现，例如「赋能」「抓手」「收口」「承载」「治理」「闭环」「口径」「打通链路」「完成适配」或「提供能力」。存在真实取舍时，直接写选择、原因、影响和失败结果。

不使用大量「不是……而是……」制造假对比。需要区分两个方案时，分别写清适用条件和结果。

中文正文使用直角引号「」。代码标识符、JSON、配置、路由和协议字面量保持原文。中文段落一段一行；代码、表格、引用和 Mermaid 保留必要换行。

## 链接、术语和图

Java 类型和项目概念使用普通文字或普通链接；方法调用、字段、枚举值、注解、配置键、路由、路径和协议字面量使用行内代码。

每个链接都必须指向能够核对当前结论的页面或章节。目录页可以作为入口，不能代替具体行为、配置或规则页面。页面合并、移动或重命名时，同步修改入站链接和锚点，不为已删除内容长期保留空转发页。

Java API 使用以下地址：

```text
/javadoc/<Gradle 项目路径>/<包路径>/<类型>.html
/javadoc/<Gradle 项目路径>/<包路径>/package-summary.html
/javadoc/<Gradle 项目路径>/index.html
```

三个以上对象协作、存在状态分支或数据归属容易混淆时，使用 Mermaid。图中使用真实模块、类型、方法、路由、配置键或数据项；图后说明关键条件、状态变化、失败位置和数据变化。没有增加信息时不使用图，也不为画图生造「平台」「中心」或「统一入口」等对象。

## 教程与参考

一篇教程完成一个可以独立验收的任务。开头直接说明完成后的结果，正文按真实操作顺序展开，到读者能够确认结果时结束。前置条件放在第一次需要它的位置，只有实际存在且常见的失败才写处理方法。

参考页集中列出准确契约，不复制完整教程或设计背景。教程、概念页、示例和参考页之间使用链接连接；不为搜索关键词或形式完整创建重复页面。

## 页面生命周期

新增页面前确认它是长期存在的概念、独立任务或需要集中维护的参考。内容能够进入已有页面时，不增加导航入口。禁止创建只有标题、TODO 或「待补充」的页面。

移动或删除页面时，先把仍有效的规则、条件、例外、失败结果、代码块和链接并入唯一责任页，再修改导航和入站链接。文件名使用小写英文和连字符，标题使用读者查找对象或动作时会采用的名称。

## 文档构建与检查

修改普通正文时，完整重读页面、检查相邻入口和运行 `git diff --check`。修改导航、内部链接、VitePress 配置、Markdown 组件或生成输入时，运行完整文档站构建。

```bash
./gradlew documentationSite
```

VitePress 构建成功只能证明 Markdown 站点可以生成，不能代替 Java API 链接检查。Javadoc 链接应当对照 `build/docs/site/javadoc/` 或 `docs/public/javadoc/` 中的实际文件确认。

## 完成条件

- 页面有明确读者和责任；
- 内容来自当前源码、配置、测试、迁移或已确认设计；
- 一项规则只有一个完整说明位置；
- 正文使用具体对象、条件、动作、结果和失败说明；
- 链接指向准确页面，导航与页面路径一致；
- 没有任务状态、历史迁移、临时双轨或无完成条件的 TODO；
- 页面可以独立阅读，并通过所需的文档构建。
