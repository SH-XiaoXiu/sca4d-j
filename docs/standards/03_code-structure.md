# 03 命名、类型与代码结构

## 目标

目录和包名先说明代码处理什么对象，再说明它负责哪类操作。熟悉一个模块后，开发者应当能够根据类名判断其所在包，也能根据包名判断其中允许出现哪些类型。

分包不是为了让目录看起来整齐。每增加一层包，都会增加查找和跳转成本；新层级必须能够稳定地区分两类职责。

## 命名和类型

名称直接说明业务对象和动作。方法使用 `createOrder`、`replacePermissions`、`findAccount` 这类名称，不使用 `process`、`execute`、`handle` 或 `doCreate` 要求读者进入实现才能理解的名称。

类名优先使用真实概念。`DTO`、`VO`、`BO`、`PO`、`Entity`、`Data`、`Info`、`Context` 和 `Manager` 只在所在边界已经赋予它们明确含义时使用。一次操作的输入或输出使用能说明结果的名称，不用后缀代替含义。

系统定义的有限状态、类型、模式和操作使用枚举或封闭的类型表达，不退化成任意字符串。开放字符串标识必须说明注册来源、校验位置和未知值结果。不使用多个布尔值表达一个只能处于某一种状态的对象。

参数在业务上本来就是一组稳定数据时才包装为类型。参数数量本身不是创建 `Context`、`Options` 或 `Payload` 的理由。项目禁止使用 Java `record`，生产代码、测试和文档示例均使用名称清楚的普通类。

引用类型的参数、返回值、字段和泛型元素按真实契约使用 JetBrains `@NotNull` 或 `@Nullable`。空值、找不到、空集合和失败结果不能混用同一种表示。

## Gradle 项目与 Java 包

Gradle 项目表示可以单独选择、替换或运行的功能，Java 包表示项目内的对象和职责。文件数量多不是拆分 Gradle 项目的理由；两个包使用不同名称，也不表示它们应当分属不同模块。

顶层项目的职责和依赖见[架构与边界](/standards/02_architecture)。新建 Gradle 项目或顶层目录时，先说明现有位置为什么不适合，并确认新边界带来的选择、替换或部署价值。

## 包名先表达对象

每个 Gradle 项目在自己的根包下组织代码。包名优先使用实际对象，例如：

```text
com.sca4d.iam.identity
com.sca4d.iam.rbac
com.sca4d.auth.passkey.credential
com.sca4d.iot.device
com.sca4d.storage.file.lifecycle
```

`identity`、`credential`、`device` 和 `lifecycle` 在这些位置都能排除一组不相关的类。只有当一个子包内已有或明确会有多个同类职责时，才建立子包；不为了包裹一个类机械地增加目录。

对象和职责已经表达清楚时，不再增加按 Java 形式分类的层级。例如 `com.sca4d.iam.identity.AccountStatus` 已经足够准确，`com.sca4d.iam.identity.enums.AccountStatus` 只补充了「这是 enum」，没有补充业务信息。

## 职责子包

以下名称只在类型确实共同承担该职责时使用：

- `request`：HTTP、消息或外部协议的输入绑定；
- `view`：HTTP 输出的字段裁剪、脱敏和展示转换；
- `repository`：隐藏 Mapper 和数据库结果的持久化操作；
- `mapper`：MyBatis Mapper 和与 SQL 形状直接对应的行类型；
- `config`：Spring 自动配置、类型化配置和启动检查；
- `security`：密钥、签名、证书和安全框架接入；
- `protocol` 或 `codec`：外部协议的字段、帧和编解码；
- `persistence`：同一对象的 Repository、Mapper 和持久化行类型确实需要作为一组隔离时使用；
- `scheduling`、`message`、`realtime` 等技术职责包：只放与该运行机制直接相关的类。

这些名称不是所有模块都必须具有的模板。一个类能够直接放在对象包中时，不为形式对称新建 `service` 或 `impl` 子包。

## 不按 Java 形式收纳

不默认建立以下包：

```text
enums/
dto/
vo/
bo/
po/
impl/
interfaces/
classes/
model/
result/
```

这些名称只说明 Java 形式，不说明类处理什么。枚举放回它所表达的对象包；Request 和 View 放在真实传输边界；Mapper 查询行放在对应 Mapper 附近；一次操作的返回类型使用能说明结果的名称。

例外是 Java 形式本身已成为一项共用技术。例如 Core API 中的 `enums` 包管理枚举编码契约时，它负责的是枚举转换机制，不是收集各模块的业务枚举。

## `Util` 与 `Helper`

`Util` 只表示无状态、输入输出清楚的通用技术操作，例如文本编码、时间格式转换或摘要计算。它不保存业务状态，不开启事务，不组合 Repository，不决定消息、通知和审计副作用。

`Helper` 只帮助一个明确对象处理有限技术细节、协议转换或测试准备。名称要说明它帮助谁、处理什么。一个 Helper 如果开始组合校验、构建、保存和发布等完整业务步骤，它已经是 Service，应当用真实业务动作命名。

不建立全局 `utils` 或 `helpers` 杂物包。多个工具共同处理文本、时间、序列化或日志等明确技术对象时，按该对象组织；无法形成类别时，类型留在它实际服务的模块。

## 主要流程不改写成函数集合

不把完整业务动作拆成一组 Util、Helper 或私有步骤方法，再由调用方手工串联：

```java
OrderHelper.validate(request);
OrderHelper.prepare(order);
OrderHelper.save(order);
OrderHelper.publish(order);
```

这些调用共同表达订单操作的校验、写入和副作用顺序，应当在 Service 主要方法中连续展示。Java Lambda、Stream 和函数式接口本身不受限制；问题在于它们是否隐藏了对象、状态变化、顺序、事务或副作用。

## 层级深度

包层级保持最浅的可读结构。增加下一层子包前，逐项确认：

1. 上一层已经包含至少两类不同职责；
2. 新层可以明确排除一组不属于它的类；
3. 调用方可以根据对象和职责预测类的位置；
4. 新层不是为了隐藏文件数量。

例如 `messaging.outbox` 成立，因为 Outbox 有自己的持久化、抢占、重试和投递职责。`iam.enums.status` 不成立，因为它连续按 Java 形式和字段类型分类，没有增加对象信息。

## 修改和移动

新增、修改、重命名和移动类型时，检查整个类的包归属，不只看本次新增方法。移动类型需要同步处理 import、Spring 扫描或自动配置、MyBatis 类型名、反射字符串、测试和文档。

未触及的历史包不因一次局部修改而全量迁移。但如果当前类必须移动才能放到真正负责它的位置，就应当在当前变更中完成消费方更新，不保留双路径或兼容壳。

## 完成条件

新增、修改、重命名和移动的类型同时满足：

- 包名和类名能够说明对象与职责；
- 传输、持久化、配置、安全和协议代码留在对应位置；
- 子包表达稳定分类，不按 Java 语法形式收纳文件；
- `Util` 和 `Helper` 没有承担业务状态机、事务和副作用顺序；
- 同类代码使用同一种位置和命名方式，没有形成第二套目录语言。

## 命名、类型与显式契约

### 命名

类、方法、字段和路由必须使用项目业务语言。动词说明动作，名词说明稳定对象；禁止 `process`、`handle`、`data`、`info` 等无法预测职责的泛化名称。

方法名按 `接收者.方法` 阅读。接收者已经表达对象时，方法名只保留动作或返回对象：`DeviceService.loadById(...)`、`IotDeviceController.get(...)`、`ProductDefinitionCatalog.definition(...)`。只有「按某个关系取得对象」本身是方法的主要含义、且名词方法会产生歧义时才使用 `For`，例如明确的解析器或策略映射。同一个方法名可以出现在不同接收者中，只要组合后的含义自然；不为了全局唯一或形式统一增加前后缀。

业务方法不使用裸 `require(...)`，也不使用 `requireActive`、`requireCurrent` 等把异常策略当作领域动作的前缀。可缺失查询返回 `Optional`、集合或分页并使用 `find...`；找不到即失败的读取使用 `loadById`、`loadByCode` 或 `loadAt`；确认已有状态使用 `verify...`、`assert...` 或状态名；向对象登记内容使用 `add...`、`register...` 或 `record...`。底层文本、数值、协议字段和影响行数断言可以使用 `require...`，但必须由接收者和参数名称明确说明校验对象。

Request 只用于 HTTP 输入，View 只用于 HTTP 输出。一次操作返回值必须使用说明业务语义的类型名，不能以泛化 `result` 包收纳；数据库映射类型由 Repository 处理。对外返回业务对象，HTTP 响应由 View 转换；不为同一个业务对象机械复制 DTO、VO、BO 等类型。

`Util` 和 `Helper` 不是禁用后缀，但必须准确描述真实的无状态通用操作或有限技术协助。处理状态机、事务、持久化调用和副作用顺序的类型必须使用对应的业务动作或对象名称。完整判断见本页的[代码结构与分包](/standards/03_code-structure)。

### 类型

有限状态必须使用枚举或封闭类型，不使用魔法字符串和整数。ID、时间、金额、权限动作和访问范围使用稳定类型；不同领域 ID 不得因底层都是 `Long` 就随意互换。

生产代码和测试代码均禁止声明 `record`。需要不可变值对象时使用语义明确的普通类，并显式声明构造器、字段访问和约束。

### 显式契约

公共和核心方法的必要输入必须出现在签名。不得从全局可变状态、ThreadLocal 或通用 Context 偷取本应由调用者明确提供的业务参数。请求级认证事实只能从当前 Call 获取。

### 空值

空值必须有明确业务含义，并通过 JetBrains nullability、Optional 或结果类型表达。禁止用 `null` 同时表示不存在、无权限、全部范围和系统错误。

### 有限状态

枚举反序列化拒绝未知值；开放字符串只用于真正开放的外部编码。状态转换由业务流程控制，不允许 Controller 或 Mapper 随意写入任意状态。
