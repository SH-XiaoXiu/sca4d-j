# 03 命名、类型与代码结构

按业务对象和职责放置代码，让类名、方法名和包名说明处理什么。新增类型前先找同类实现；类和接口应有清楚的职责，私有方法应改善局部表达且不割裂主要流程。

## 目标

目录和包名先说明代码处理什么对象，再说明它负责哪类操作。熟悉一个模块后，开发者应当能够根据类名判断其所在包，也能根据包名判断其中允许出现哪些类型。

分包不是为了让目录看起来整齐。每增加一层包，都会增加查找和跳转成本；新层级必须能够稳定地区分两类职责。

## 命名和类型

业务类、方法、字段和路由使用所属领域的语言。动词说明动作，名词说明对象；`process`、`handle`、`data`、`info` 等名称只有在接收者与上下文已经明确其含义时才使用。框架要求的方法名保持框架约定。

方法名与接收者一起表达含义。例如 `OrderService.loadById(...)` 中，接收者已说明要读取订单，方法名只需说明按 ID 读取。`OrderController.get(...)` 和 `CategoryCatalog.definition(...)` 也应按完整调用阅读，不为了让方法名全局唯一而重复对象名称。

关系本身决定调用结果时，方法名应保留必要的 `For` 或 `By`；关系已经由接收者和参数说明时，不机械追加后缀。

读取与校验方法还应让调用方知道「找不到」会怎样。`findAccount(...)` 可以返回 `Optional`，`loadAccount(...)` 表示找不到即失败，`verifyActive(...)` 检查已取得账号的状态。这些名称是含义示例，不是每个项目的固定词表。裸 `require(...)` 或 `requireActive(...)` 若只说明异常策略，仍需结合接收者判断实际业务含义。

`Request` 表示一个明确协议或操作的输入，`View` 表示 HTTP 输出；名称与包位置应能说明它们属于哪个协议或操作。一次操作的返回类型使用业务含义命名，数据库映射类型由 Repository 处理。HTTP 响应由 View 转换；不为同一个对象机械复制 DTO、VO、BO 等类型。

假设创建账号的 HTTP 输入类型名为 `CreateAccountRequest`，它只承接请求字段；Service 接收已校验的创建参数，Repository 处理数据库行。数据库新增内部审计列时，请求类型不需要增加同名字段。这里需要区分输入与存储的职责，而不是为每层复制一份内容相同的 Account。

`Util` 和 `Helper` 不是禁用后缀，但必须准确描述真实的无状态通用操作或有限技术协助。处理状态机、事务、持久化调用和副作用顺序的类型必须使用对应的业务动作或对象名称。完整判断见本页的 `Util` 与 `Helper` 章节。

参数在业务上本来就是一组稳定数据时才包装为类型。参数数量本身不是创建 `Context`、`Options` 或 `Payload` 的理由。

例如，金额与币种始终一起校验、比较和计算时，可以形成金额类型；`accountId`、`operatorId`、`sendNotification` 仅因某个方法参数较多而被放进 `AccountContext`，仍是几个含义不同的输入。

### 类型

有限状态、模式和操作使用枚举或封闭类型。开放字符串必须说明注册来源、校验位置和未知值结果；不使用多个布尔值表示只能处于一个状态的对象。枚举反序列化拒绝未知值，Controller 和 Mapper 不自行决定状态转换。

ID、时间、金额、权限动作和访问范围使用能够表达各自含义的类型。不同领域 ID 不能因底层都是 `Long` 就任意互换；需要不可变值对象时，应明确构造条件、字段访问和相等性约束。项目是否使用 Java `record` 由其语言与代码约定决定。

### 显式约定与空值

核心方法的必要输入直接出现在签名中，不从全局可变状态、ThreadLocal 或通用 Context 获取本应由调用者提供的业务参数。请求级认证事实从当前 Call 获取。

引用类型的参数、返回值、字段和泛型元素根据真实约定使用 JetBrains `@NotNull` 或 `@Nullable`。空值要有单一、明确的业务含义；不能同时表示不存在、无权限、全部范围和系统失败，可按实际情况使用 Optional 或专用结果类型。

## Gradle 项目与 Java 包

构建模块表示具有独立所有权、可选择或可替换的功能，Java 包表示模块内的对象和职责。文件数量多不是拆分模块的理由；两个包使用不同名称，也不表示它们应当分属不同模块。

模块负责什么及怎样协作见[功能归属与调用关系](/standards/02_architecture)。新建构建模块时，现有位置无法承担的职责及独立选择、替换或部署的价值应当清楚；具体目录由仓库指令规定。

## 包名先表达对象

每个模块在自己的根包下组织代码。包名优先使用实际对象，例如：

```text
com.example.identity.account
com.example.identity.permission
com.example.authentication.credential
com.example.device.connection
com.example.storage.file.lifecycle
```

`account`、`credential`、`connection` 和 `lifecycle` 在这些位置都能排除一组不相关的类。只有当一个子包内已有或明确会有多个同类职责时，才建立子包；不为了包裹一个类机械地增加目录。

对象和职责已经表达清楚时，不再增加按 Java 形式分类的层级。例如 `com.example.identity.account.AccountStatus` 已经足够准确，`com.example.identity.account.enums.AccountStatus` 只补充了「这是 enum」，没有补充业务信息。

## 职责子包

以下名称只在类型确实共同承担该职责时使用：

- `request`：HTTP、消息或外部协议的输入绑定；
- `view`：HTTP 输出的字段裁剪、脱敏和展示转换；
- `repository`：隐藏 Mapper 和数据库结果的持久化操作；
- `mapper`：MyBatis Mapper 和与 SQL 结构直接对应的行类型；
- `config`：Spring 自动配置、类型化配置和启动检查；
- `security`：密钥、签名、证书和安全框架接入；
- `protocol` 或 `codec`：外部协议的字段、帧和编解码；
- `persistence`：同一对象的 Repository、Mapper 和持久化行类型确实需要作为一组隔离时使用；
- `scheduling`、`message`、`realtime` 等技术职责包：只放与该运行机制直接相关的类。

这些名称不是所有模块都必须具有的模板。一个类能够直接放在对象包中时，不为形式对称新建 `service` 或 `impl` 子包。

## 不按 Java 形式收纳

不默认建立以下包：

```text
enums/
dto/
vo/
bo/
po/
impl/
interfaces/
classes/
model/
result/
```

这些名称只说明 Java 形式，不说明类处理什么。枚举放回它所表达的对象包；Request 和 View 放在对应协议的输入、输出位置；Mapper 查询行放在对应 Mapper 附近；一次操作的返回类型使用能说明结果的名称。

例外是 Java 形式本身已成为一项共用技术。例如专门管理枚举编码约定的 `enums` 包负责转换机制，而不是收集各模块的业务枚举。

## `Util` 与 `Helper`

`Util` 只表示无状态、输入输出清楚的通用技术操作，例如文本编码、时间格式转换或摘要计算。它不保存业务状态，不开启事务，不组合 Repository，不决定消息、通知和审计副作用。

`Helper` 只帮助一个明确对象处理有限技术细节、协议转换或测试准备。名称要说明它帮助谁、处理什么。一个 Helper 如果开始组合校验、构建、保存和发布等完整业务步骤，它已经是 Service，应当用真实业务动作命名。

不建立全局 `utils` 或 `helpers` 杂物包。多个工具共同处理文本、时间、序列化或日志等明确技术对象时，按该对象组织；无法形成类别时，类型留在它实际服务的模块。

## 主要流程不改写成函数集合

不把完整业务动作拆成一组 Util、Helper 或私有步骤方法，再由调用方手工串联：

```java
OrderHelper.validate(request);
OrderHelper.prepare(order);
OrderHelper.save(order);
OrderHelper.publish(order);
```

这些调用共同表达订单操作的校验、写入和副作用顺序，应当在主要业务方法中连续展示。独立的算法或复杂条件可以抽出，但调用处要保留它对业务流程的意义。Java Lambda、Stream 和函数式接口本身不受限制；问题在于它们是否隐藏了对象、状态变化、顺序、事务或副作用。

## 层级深度

包层级保持最浅的可读结构。增加下一层子包前，逐项确认：

1. 上一层已经包含至少两类不同职责；
2. 新层可以明确排除一组不属于它的类；
3. 调用方可以根据对象和职责预测类的位置；
4. 新层不是为了隐藏文件数量。

例如 `messaging.outbox` 成立，因为 Outbox 有自己的持久化、抢占、重试和投递职责。`iam.enums.status` 不成立，因为它连续按 Java 形式和字段类型分类，没有增加对象信息。

## 修改和移动

新增、修改、重命名和移动类型时，检查整个类的包归属，不只看本次新增方法。移动类型需要同步处理 import、Spring 扫描或自动配置、MyBatis 类型名、反射字符串、测试和文档。

未触及的历史包不因一次局部修改而全量迁移。但如果当前类必须移动才能放到真正负责它的位置，就应当在当前变更中完成消费方更新，不保留双路径或兼容壳。
