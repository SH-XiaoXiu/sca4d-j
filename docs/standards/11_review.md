# 11 代码评审

评审先确定变更的完整范围，再沿调用方核对行为、依赖、失败和并发。每个结论都应说明依据，以及哪些行为尚未验证；编译成功、代码行数或方法名称不能单独证明设计正确。

## 建立范围

使用 Git 状态和差异建立新增、修改、重命名、删除及未跟踪文件的清单。逐个阅读改动文件的完整内容，删除文件检查原有职责和消费者是否已处理。再沿公开接口约定查找直接调用方、实现方、配置、迁移、测试和文档。

差异规模超过一次评审能够完整覆盖的范围时，按职责拆分变更。未读文件和未执行检查应明确列出，不使用抽样结果声称已经覆盖全部改动。

## 先审行为，再审结构

先确认需求对象、允许的状态变化、权限、事务、并发结果和外部副作用。随后检查代码是否位于负责该行为的位置，名称和参数是否让调用方理解成功与失败结果。

检查类型和方法是否为当前问题选择了必要的特征、行为与关系；对象封装是否维护状态和不变量；私有方法拆分是否帮助阅读完整流程。只转发、绑定常量或复制字段的类型与方法，需要说明它们实际承担什么职责。对同类功能，检查目录、API、错误处理和验证方法是否保持可预测。

例如，停用账号的改动即使只发生在 Service，也要沿调用方核对 HTTP 权限、Repository 的条件写入、会话失效时机和失败结果。若新增的 Manager 只把相同参数转给 Service，它没有承担新的行为；若它负责一个独立的事务或外部协议转换，则需按实际职责命名并检查调用结果。

接口、普通类、枚举和参数对象按实际职责选择。存在多个实现、明确扩展点或调用方不应依赖具体实现时，接口可能成立；固定实现不机械增加接口与 `Impl` 配对。有限状态使用类型约束，开放字符串写清来源、校验位置和未知值结果。

## 检查实现职责

- HTTP 输入与响应转换不承担业务状态机；业务层不操作数据库列、影响行数或传输框架内部对象。
- SQL 的范围、排序、批量上限和原子写入条件与业务结果一致；列表和循环检查实际数据库与外部调用数量。
- 事务内写入、提交后结果与外部系统确认分开描述；失败、重试、部分成功和幂等结果可以恢复。
- 多实例同时处理共享数据时，数据库条件、租约或分布式协调决定竞争结果；单机锁和内存状态不承担集群一致性。
- 日志保留排查所需的阶段与对象标识，不重复记录同一异常，不暴露凭据、完整 Payload 或不必要的个人数据。
- 前端检查受影响页面的加载、空状态、操作、失败恢复、权限变化、焦点与窄屏结果；静态截图不代替交互验证。

评审按改动影响选择「检查实现职责」中列出的检查。没有数据库访问的文件不填写虚构的 SQL 结果；没有视觉变化的改动不把未执行的浏览器检查写成通过。修改过的文件若存在直接影响当前行为的既有问题，应一并处理。无关的历史问题另行记录，不借评审扩大本次改动范围。

## 注释、测试与文档

公开 API 的文档注释说明调用条件、数据变化和失败结果。私有方法只有在名称和代码不足以说明非直观约束时添加注释；不要用注释为没有职责的步骤包装辩护。逻辑注释解释原因、顺序和不变量，不逐行翻译代码。

测试通过公开行为验证目标约定。单元测试、框架装配、数据库集成和浏览器检查分别说明自己覆盖了哪些行为。配置、接口、数据和操作方式变化时，检查负责说明它们的文档是否仍然准确。

## 评审记录

评审结果至少包含：改动文件及必要消费者、已读与未读文件、发现的问题及位置、实际执行的检查与结果、未验证的行为。问题按影响结果和可恢复性排序；无法确认的事实写明缺少什么证据。

提交前确认目标行为完整、必要的旧入口已清理、检查结果与说明一致、没有敏感信息，且差异中没有无关改动。失败命令应区分代码问题、环境问题和覆盖缺口。
