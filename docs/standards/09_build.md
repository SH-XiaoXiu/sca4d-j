# 09 格式化与构建

编译检查类型和依赖，测试检查行为，格式化检查文本，静态审计发现工程问题，构建生成产物。先说明修改可能破坏什么，再选择覆盖这些风险的任务。具体命令、工具版本、项目路径和资源限制由仓库指令及构建文档维护。

## 选择检查

| 修改内容 | 至少需要的证据 |
| --- | --- |
| 类型、签名或依赖变化 | 直接受影响项目的编译，以及必要消费者的编译 |
| 业务规则变化 | 覆盖新旧结果、失败和边界情况的测试 |
| 框架装配与配置变化 | 启动或最小上下文中的真实装配检查 |
| 数据库迁移变化 | 新库安装和已有数据升级的相关检查 |
| 前端类型或状态变化 | 类型检查及受影响流程的测试 |
| 布局和交互变化 | 实际页面在相关状态、尺寸和操作下的检查 |
| 构建入口、依赖或发布资源变化 | 对应构建产物的生成与检查 |

局部修改优先运行能直接发现问题的项目任务。跨模块公开接口约定变化需要检查直接消费者；发布或确实影响整个工程时，再运行全仓库检查。环境或依赖缺失时，记录实际失败和未覆盖风险，不把未执行任务写成通过。

例如，修改一个 Java 类型的文档注释，重点是对应 API 文档能否生成、链接是否仍指向该类型；修改自动配置的 Bean 选择条件，则需要覆盖「没有实现」「一个实现」「多个实现」的装配结果。两类变化即使都能编译，也需要不同证据。

## 格式化与审计

格式检查以仓库现有工具的配置为准。会写文件的格式化命令运行前，先确认目标范围没有不属于当前任务的修改；无法隔离时只运行只读检查并修正本次改动。

格式正确不证明命名、分层、SQL、文档事实或运行行为正确。静态审计结果按文件与规则判断；不通过批量抑制或排除配置掩盖本次引入的问题。与本次目标无关的既有问题单独报告。

## 文档与生成结果

普通正文变化需要核对事实和差异；导航、内部链接、Markdown 组件或站点配置变化需要构建文档站。文档站构建成功不能证明外部链接、生成的 Java API 地址或正文事实正确。

生成结果从源文件和构建任务重新产生，不手工修补。已经发布并被数据库使用的版本迁移属于受控源文件，后续变化通过新迁移向前升级。需要随源码提交的生成物，应由项目发布约定明确列出。
