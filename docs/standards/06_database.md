# 06 数据库规范

每张表由一个模块或具体应用负责，约束保护数据完整性，索引服务实际查询。新应用从结构片段生成首份迁移，已有数据库通过新增 Flyway 迁移升级；修改前同时检查新库安装、旧数据转换和失败恢复。

Mapper 与 Repository 的职责见[SQL 与持久化](./05_persistence)，业务字段接入见[开发后端业务接口](/tutorials/backend-feature)。

## 数据归属

每张表由保存这类数据的模块或 App 负责。模块只能维护自己的表、索引和结构片段，不直接修改另一个模块的数据。App 可以保存自身业务数据，但不能把模块内部表当成 App 的 Repository 接口。

新增表前先回答：哪些数据需要长期保存，哪个模块负责创建、查询、修改和删除，相关功能被移除后这些数据怎样处理。页面临时状态、可以可靠重算的值和一次请求中的中间结果不写入数据库。

## 表、列与类型

- 表名和列名使用小写下划线，名称直接说明保存的对象和事实。
- 主键、引用列和 Java 类型保持一致。ID 不编码租户、权限、状态或创建时间等额外含义。
- 时间点使用 `TIMESTAMP WITH TIME ZONE`，持续时长和数量在名称或注释中写明单位。
- 系统定义且取值有限的状态使用稳定编码，并与 Java 枚举或专用类型一致。数据库不保存展示中文、Java 枚举序号或页面标签。
- `JSONB` 只保存结构确实会扩展，或 PostgreSQL 需要按 JSON 内容查询的数据。字段固定时使用明确列。
- `NULL` 必须表示一种清楚的业务情况。必填数据使用 `NOT NULL`；不要用空字符串、零或特殊日期代替缺失值。
- 默认值只用于所有写入入口都成立的初始事实。依赖调用方、当前身份或业务流程的值由 Service 明确提供。

## 约束

数据库约束只表达数据库能够独立判断的条件：

- 主键保证记录唯一；
- 唯一索引防止并发请求写入重复数据；
- `NOT NULL` 防止必填列缺失；
- `CHECK` 限制单行内的状态编码、数值范围、成对空值和字段组合；
- 原子 `UPDATE` 的条件同时检查版本、当前状态和必要的数据范围。

当前 Sca4d-J 模块结构没有建立物理外键。跨表引用以 ID 保存，由负责该业务动作的 Repository 在写入时确认目标，并由删除或清理流程处理后续数据。新增关系继续采用这一做法，除非相关模块设计已经明确改为物理外键；不能只在一张表上临时改变引用规则。

数据库约束和 Java 校验不能互相冒充。Java 类型负责让调用方不能构造明显错误的参数，数据库负责阻止并发写入破坏能够由当前表直接判断的条件。跨模块状态、权限和完整业务流程仍由 Service 与 Repository 判断。

## 索引

索引来自真实查询和写入条件，不按「常用字段」猜测添加。设计索引时同时检查：

- `WHERE` 中的等值、范围和逻辑删除条件；
- JOIN 使用的引用列；
- 分页和任务抢占的排序；
- 唯一性是否只对未删除或有效记录成立；
- 更新、删除和批量写入需要维护索引的成本。

逻辑删除数据的唯一性通常使用带删除条件的部分唯一索引。按时间倒序分页时，索引顺序应与查询的稳定排序一致，并包含用于消除同一时间值歧义的 ID。没有查询依据的重复索引应删除。

重要查询在具有代表性的数据量下检查执行计划。测试库数据很少时，「查询很快」不能证明索引正确；需要结合 SQL 条件和执行计划判断。

## 删除与历史记录

只有需要恢复、追溯、保留引用或隔离唯一键复用的数据使用逻辑删除。逻辑删除列进入所有正常查询、唯一索引和状态变更条件。

可重建关系、短期 Challenge、幂等窗口和清理任务记录可以按各自生命周期直接删除。审计、事件和执行历史等只追加数据不通过普通更新改写结果；更正需要新增记录时，使用能够说明原记录和更正关系的字段。

## 模块结构片段与 App 迁移

需要数据库的模块把新 App 应具有的当前结构保存在：

```text
src/main/resources/META-INF/sca4dj/schema/<name>.sql
```

App 自己的结构片段放在 `src/main/resources/schema/app.sql`。App 第一次建立数据库时，`initFlyway` 按运行依赖顺序合并模块片段，再追加 App 片段，生成 `V1__init_<app>.sql`。

生成后的 V1 由 App 维护。模块结构后来发生变化时，需要同时处理两类对象：

- 更新模块结构片段，使以后创建的新 App 得到最新结构；
- 已经存在迁移历史的 App 新增 V2、V3 等迁移，使现有数据库继续向前升级。

不能重新运行 `initFlyway` 覆盖已有迁移，也不能只改模块片段后假设现有 App 会自动升级。独立数据源，例如 IoT TimescaleDB，使用所属模块自己的 Flyway 位置和事务管理器。

## Flyway 迁移

已经在共享环境执行的迁移不修改文件名、内容和校验和。后续变化新增 `V<N>__<description>.sql`。

迁移同时考虑空数据库和已有数据：

- 新增非空列时，说明已有行怎样获得合法值；
- 删除、重命名或转换列前，先验证目标数据和所有读写位置；
- 创建唯一索引前，先检查重复数据；
- 大表更新、索引创建和类型转换需要评估锁时间与失败恢复；
- 数据回填需要明确目标集合、批次、幂等性和重复执行结果；
- 迁移失败时不能依赖本机脚本或未记录的人工步骤才能恢复。

生产迁移不根据当前机器、时间随机值或外部服务返回结果决定结构。确需分阶段发布时，每个阶段都要有可运行的表结构和代码组合，不能在正式文档中把临时双轨写成最终设计。

## 完成条件

数据库修改完成时，应当能够确认：

- 表和数据有明确负责模块；
- SQL、Java 类型、Mapper、Repository 和文档使用相同含义；
- 约束能够阻止并发下的重复值和非法单行状态；
- 索引对应真实查询、排序和唯一性条件；
- 新 App 的结构片段与已有 App 的后续迁移都已处理；
- 新库安装、旧库升级、数据回填和失败恢复都有对应检查。
