# 01 工程原则

先确定对象、数据归属和完整业务动作，再选择最容易理解和验证的实现。核心接口保持稳定，具体场景留在外围流程，只有独立功能才建立抽象；评审时检查调用者能否看清条件、变化和失败结果。

本页解释设计选择的判断依据，目录、持久化和构建的具体要求由各自规范负责。

## 稳定核心，丰富边缘

核心 API 的名称、参数和结果应保持稳定。业务场景的差异放在外围流程中，不通过不断增加布尔参数、可空参数和特殊分支改变核心 API。

例如，`createOrder(...)` 表示创建订单。人工创建、批量创建和后台导入如果拥有不同的权限、状态变化或外部副作用，应分别处理这些差异，再调用真正共用的底层动作。几种场景最后都写入同一张表，不足以证明它们应该共用一个包含大量选项的核心方法。

**判断标准：**复用取决于输入、业务规则、状态变化、失败结果和副作用是否相同，不取决于最后是否执行同一条 SQL。

## 一个对象只保留一套含义

一个概念只保留一套名称、一套运行模型和一个事实来源。

以下情况说明系统出现了重复含义：

- 前端和后端分别计算同一个业务字段，并可能得到不同结果；
- 数据库、缓存和请求上下文分别保存同一个状态；
- 同一个请求或身份在不同模块重复创建上下文对象；
- 同一个路由、配置项或默认值在多处维护；
- 同一个操作存在绕过正常检查的旁路入口；
- 新旧名称、字段或路由同时保留，却没有明确哪一个是当前契约。

拥有数据的字段、对象或 Service 是事实来源。其他位置可以读取、缓存或转换，但不能重新定义一套可能不同的结果。

## 只为独立功能建立抽象

类、接口、私有方法、Builder、Factory、Context、Manager、Helper 和包装对象，只有在能够独立命名、独立理解并具有稳定输入输出时才有价值。

以下结构通常没有形成新概念：

- 只转发另一个方法；
- 只复制一两个字段；
- 只绑定一个常量；
- 只把完整流程拆成 `prepare`、`build`、`validate`、`execute`、`after` 等步骤；
- 只为未来可能出现的需求预留扩展点；
- Mapper 和 Repository 一一对应、参数和结果都原样传递。

抽象的价值在于隐藏调用方必须重复理解的真实细节，例如协议转换、乐观锁结果、权限判断或稳定的聚合读写。缩短方法或减少几行重复代码本身不是建立抽象的理由。

## 主要流程保持连续

核心业务方法应让开发者从上到下看到校验、判断、状态变化、持久化和副作用的顺序。方法较长并不自动表示设计有问题；为了缩短方法而增加跨文件跳转、隐藏事务边界或分散失败处理，通常会增加理解成本。

私有方法只有在表达独立业务行为、算法、协议转换或框架边界时才保留。只表示执行步骤的方法应放回主要流程，避免阅读者在多个 `prepare`、`build` 和 `after` 方法之间来回寻找真实顺序。

**判断标准：**阅读者不需要依赖作者记忆，就能判断每次写入何时发生、事务覆盖什么、事件何时发布，以及失败后保留哪些数据。

## API 是项目语言

API、类型、字段、包和路由名称共同构成项目的工作语言。名称应直接说明对象和动作，例如 `disableAccount`、`replacePermissions`、`findAccount` 和 `claimForDispatch`。

`process`、`handle`、`execute`、`doCreate`、`data`、`info`、`context` 和 `manager` 等名称不能代替真实业务含义。`Request`、`View`、`Result`、`Payload` 和 `Entity` 只有在类型确实承担对应边界职责时才使用。

方法名描述成功时发生的动作，不把「会抛出异常」作为统一命名规则。可缺失查询使用 `find...`，找不到即失败的读取使用 `load...`，已有事实复核使用 `verify...` 或 `assert...`，对象登记使用 `add...`、`register...` 或 `record...`。底层输入断言可以使用 `require...`，但接收者必须明确说明被校验的对象。

相邻模块中已经稳定重复的目录、调用方式、参数形状和失败结果构成项目样板。新增功能应延续可预测的样板；业务差异可以保留独立流程，但不能因此建立第二套目录语言。

## 显式契约优于隐藏状态

核心方法的必要输入应出现在参数中。只有一组数据已经形成稳定概念，并且总是一起产生、校验和使用时，才包装成对象。参数数量本身不是创建 `Context`、`Options` 或 `Payload` 的理由。

权限、事务、锁、失败结果和外部调用也必须能从主要流程中看出。不要把调用者必须知道的业务行为隐藏在全局状态、ThreadLocal、默认值、拦截器或事件中。

可以在编译期表达的限制，使用 Java 类型、泛型、枚举和 JetBrains 注解表达。不要用字符串、布尔值、通用 Map 或运行时约定代替稳定类型。

## 数据库只保存稳定事实

数据库保存需要长期存在、需要并发保护或无法可靠重建的数据。页面选中项、临时步骤、可以由现有字段计算的计数和一次请求中的中间结果默认不持久化。

确实需要保存派生结果时，同时定义唯一写入方、更新时机、失效规则、修复方式和验证方法。不同身份引用同一种主体时，共用稳定主体引用，由各自模块保存角色或资料扩展，不把短期页面角色固化到公共表结构。

表结构、Java 类型、Repository、Mapper 和文档必须使用同一套含义。数据库约束负责稳定的数据完整性；Service 和领域模型负责完整业务规则；类型系统负责有限状态和输入约束。

## 类型表达有限状态

系统定义且取值有限的状态、类型、模式、操作和类别使用枚举或专用值类型。数据库使用字符串列，或 HTTP 最终序列化为字符串，都不改变 Java 内部的类型约束。

只有租户自定义编码、外部提供方名称和其他确实开放的标识可以使用字符串。保留开放字符串时，必须说明扩展来源、校验位置和未知值结果。无法证明开放性的状态字段按有限集合处理。

项目禁止使用 Java `record`。需要值对象时使用名称清楚的普通类，在构造方法和方法契约中表达输入限制。

## 优先使用已有机制

框架和 Sca4d-J 已经提供所需结果时，优先使用现有入口。自定义解析、转换、路由匹配、序列化、缓存、消息拓扑、权限匹配和生命周期管理，只有在现有机制不能表达新增的稳定含义时才成立。

自定义实现必须说明新增的输入、输出、所有权和失败结果。不能只包装一次 Spring、MyBatis、Jackson、Sa-Token 或消息框架调用，也不能让业务代码依赖容器内部状态。

## 删除旧实现优于长期兼容

Sca4d-J 不是公共 SDK。旧逻辑确认废弃后直接删除，Git 保存历史，源码只描述当前有效行为。

重命名和边界调整必须同步更新调用方、测试、配置、数据库迁移、文档和前端。不要长期保留 deprecated 壳、双路由、双字段、兼容分支和重复入口，让开发者持续判断哪一套才是事实。

只有存在明确外部消费者、迁移窗口和删除条件时，兼容入口才有理由暂时保留。

## 可预测的工程结构

架构最终应表现为可重复的代码形状、配置位置和验证方法。重复出现的业务功能应当能够预测：

- 文件和包放在哪里；
- 类型和方法怎样命名；
- 请求从哪一层进入；
- 数据范围在哪一层应用；
- 失败和并发怎样验证。

稳定重复的目录、API、数据库字段和调用顺序属于项目语言。不能只为减少表面重复而引入通用 Map、动态路由、反射分派或没有业务含义的中间层。

已经解决的分层、并发、权限、配置和运行问题，应固化到代码样板、规范和测试中。新结构只有在说明现有样板无法表达的具体含义、受影响的调用方和后续同类功能的使用方式时才成立。

**合格的工程结构应满足：**新文件位置可以从目录预测；同类 API 使用相同参数和失败结果；没有第二套请求、权限、消息、文件或配置入口；主要流程无需频繁跨文件跳转；测试覆盖多实例、失败和恢复；文档包含当前定义和准确参考。

## 变更保持一致

功能完成不仅表示源码可以编译，还表示相关表面使用同一套最终契约：

- 源码和公开 API；
- 配置和环境示例；
- 数据库迁移和测试数据；
- 前端调用方和错误处理；
- 测试、日志、事件和通知；
- 教程、参考和工程规范。

重命名和边界调整完成后，不保留旧名称、旧路由、重复默认值和过期说明。只证明编译通过不能证明契约已经一致。

## 证据优先

设计和故障判断以实际代码、数据库、请求响应、日志、构建产物、测试或运行调用链为依据。不能只根据相邻代码、方法名称或一段 diff 推断根因和完成结果。

未覆盖目标行为的成功命令不能证明功能完成；没有观察到的页面、设备或外部服务结果不能写成已验证。不同证据分别说明它证明了类型、装配、数据、业务行为还是用户界面。

## 范围纪律

变更范围包含目标功能及其必要影响面，不包含无关的历史整理。工作树中与目标无关的修改保持原状，不回滚、不覆盖，也不混入当前变更。

范围外技术债只有在直接导致目标错误、无法验证或破坏已确认契约时才进入本次修改。发现新的架构问题时，先记录它与当前结果的直接关系，不用旁路重构掩盖未确认的决定。

## 完成条件

新增或修改的类型、方法、字段和配置同时满足：

1. 表达可以独立说明的对象或技术职责；
2. 位于负责该职责的模块、目录和分层；
3. 没有复制已有概念或公共入口；
4. 抽取的结构表达独立行为，而不是流程步骤；
5. 没有重复实现框架或项目已有机制；
6. 调用方、测试、配置、日志和文档使用同一套当前契约；
7. 失败、并发和恢复结果可以由直接证据验证。

任一条件不成立时，实现还没有达到工程规范要求。
