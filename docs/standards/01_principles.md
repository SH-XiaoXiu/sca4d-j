# 01 工程设计原则

面对同一个需求，有的代码表达清楚、前后自洽，能被复用，也能被扩展；有的代码只实现了眼前的需求，下一个需求来时只能重写。差别在于分析、拆解、建模和设计的能力。这些能力主要来自两种思维：抽象和封装。本页先说明这两个概念，后面各页的规则都是它们在具体问题上的应用。

## 抽象

抽象是为一个问题建立模型：从具体的事物中找出共同的、稳定的部分，形成一个概念，再用这个概念去解释各种具体情况。抽象不是某种编程范式，面向对象（OOP）只是实现它的一种方式。

OOP 中最基本的一种抽象是类型抽象，也叫泛化。苹果、香蕉、橙子都有重量和产地，都可以吃，于是得到「水果」；继承让苹果拥有水果的全部特征，多态让只依赖「水果」的代码可以处理任何一种水果。在 Java 里判断一个继承关系对不对，把它读一遍：`Apple is a Fruit` 成立，继承大概率是对的；`Penguin is a Bird` 成立，但如果 `Bird` 声明了 `fly()`，这个继承就有问题。这是针对 OOP 类型关系的判断方法，不是抽象本身的判断标准。

项目里的例子：`Dictionary` 表示一个枚举常量可以作为前端选择项并属于某个字典，`IdentityStatus` 和 `RoleStatus` 都实现了它，接受 `Dictionary` 的代码不需要知道具体是哪个枚举。`Resource` 声明了 `type()` 和 `id()`，`PermissionPolicy.decide(Call call, Permission permission)` 判断的目标由 `Permission` 中的 `Resource` 给出，所以新增一种业务对象，只要能提供这两个值，就能成为权限判断的目标。

### 抽象是否合适

抽象保留下来的信息，能不能稳定地解释现有的需求和可能出现的需求，是判断抽象是否合适的标准。

不能解释，或者必须扭曲之后才能解释，说明抽象不对。扭曲解释是最常见的错误：需求变化时不修改模型，而是把新含义塞进已有的字段或类型。假设订单只有一个 `status` 字段，后来要支持「部分发货」，于是写入 `PARTIAL_2_OF_5`。每处读取 `status` 的代码都要知道这个约定，原来的模型并没有真正解释新需求。

另一种错误是过度抽象，抽象到没有意义。Java 中所有类型都是 `Object`，这已经足够抽象，却对业务建模毫无帮助。方法参数写成 `Map<String, Object>` 也是同样的问题，调用方看不出该传什么。

## 封装

封装是屏蔽底层，对外提供更上层、更具体的含义。它依赖底层的行为和逻辑，只是把它们包装起来，所以是扁平的：下层不存在，这一层就无法成立。抽象则是逻辑上建立的概念，不依赖具体实现也能成立：`IdentityStatus` 的 `ACTIVE` 和 `DISABLED` 没有数据库、没有 HTTP 时仍然有意义。一个封装层如果有了独立于下层的概念，说明其中混入了抽象。

后端的分层都是封装。以修改 Account 状态为例：

- `IdentityMapper.updateAccountStatus(id, status)` 执行一条 SQL，返回影响行数 `int`；
- `IdentityRepository.updateAccountStatus(id, status)` 通过 `AffectedRowCounts.changed(...)` 把影响行数解释为 `boolean`；
- `IdentityService.changeAccountStatus(id, status)` 在目标不存在时抛出 `BusinessException(IamErrorCode.ACCOUNT_UNAVAILABLE)`，成功后记录日志。

每一层依赖下一层的行为，把它换成更上层的含义，调用方不再接触 SQL 和影响行数。各层职责见 [02 功能归属与调用关系](/standards/02_architecture)。

封装也用来保护规则。假设订单规定只有「待提交」状态可以提交，类就不提供 `setStatus(...)`，而是提供 `submit()`，由方法检查状态后再修改，外部代码无法绕过。字段全部私有，但类里只有 getter 和 setter、没有任何规则，没有封装任何东西。

封装对外承诺的含义必须稳定，场景的差异留在调用方。`createOrder(...)` 表示创建订单，人工创建、批量创建和后台导入各自处理权限、输入和外部副作用，再调用它。为了让三个场景共用入口而增加 `boolean fromImport` 和一组可空选项，会使 `createOrder(...)` 的含义随场景改变。

两段代码相似不是合并的理由。是否合并，看它们表达的是不是同一个概念：输入、规则、状态变化、失败结果和副作用都相同才共用。假设创建订单和创建账号都是「校验、保存、发通知」，但校验的内容不同、各自变化，合并成 `createEntity(type, Map)` 就是过度抽象。只有 SQL 相似时，各自保留业务流程，只在 Repository 或 Mapper 中共用写入语句。

## 例：IAM 的身份设计

常见的做法是一张 `user` 表，姓名、登录名、密码、角色、状态放在一起。假设同一个人要增加企业单点登录账号，只能再插一行，靠约定关联；同一个人在两个租户任职，就要把租户和角色编码进某个字段。每次都是扭曲 `user` 的含义来解释新需求。

IAM 把它拆成三个概念，见[身份与访问](/home/identity)：Subject 表示实际接入的是谁，Account 表示通过哪个账号认证，Principal 表示当前以什么业务身份工作。同一个人增加 SSO 账号只增加一个 Account；停用管理账号不影响其他 Account；租户成员退出只停用对应的 Principal。这个模型也能解释顾客同时成为骑手这类还没有出现的需求，所以它是合适的抽象。简单场景下，IAM 另外提供 `User` 组合这三个对象。

## 完整的业务流程

一个业务动作的校验、判断、写入和副作用共同决定结果，应当在同一个方法里从上到下读完。拆成 `prepare`、`build`、`execute`、`after` 四个私有方法，读者要在四处之间拼接顺序，也看不出事务从哪里开始、通知在哪一步发出。方法长一点没有关系，只要它始终在完成同一个业务动作。

有独立名称的算法（计算签名）、协议转换（解析设备报文）、需要名称才能说明含义的复杂判断，可以提取，调用处仍要能看出它在流程中的位置。关键写入的时机、事务范围和外部调用留在主流程里。

把流程强制拆成固定的几步，是多人、多团队协作时用统一流水线换取可维护性的办法。本项目是单体，不为这种协作规模设计，所以按业务本来的顺序连续书写。

## 名称与类型

类型、方法、字段和路由合起来，是团队描述业务的语言。`changeAccountStatus`、`activeAccountById`、`findAccount` 一看就知道对象和动作；`process`、`handle`、`execute` 要进入实现才知道。框架规定的回调名称保持框架约定。

方法名还要说明找不到时的结果：`findAccount(id)` 返回 `Optional<Account>`，`activeAccountById(id)` 在账号不存在或没有启用时抛出 `BusinessException`。

会影响结果的输入直接写在签名里。一组数据在业务上本来就是整体才包装成对象，例如金额和币种。`accountId`、`operatorId`、`sendNotification` 只因参数多就放进 `AccountContext`，仍是三个含义不同的输入。权限检查、事务、锁和外部调用的位置要能从主流程看出来，不藏在默认值、拦截器或事件里。

选择类型：取值有限、由系统定义，用枚举；多个字段始终一起校验、一起比较，用值类型；取值由外部提供方或租户增加，用字符串，并写明编码来源、校验位置和未知值的处理方式。数据库和 HTTP 最终是字符串，内部保持枚举，只在 JSON、SQL 和协议出入口转换。

## 数据

数据库保存业务上最小的一组事实。字段能由其他已保存的事实推导出来，默认不设计。订单总额由明细计算得出，默认读取时计算，不另建 `total_amount` 列；已有删除时间，就不另建 `is_deleted`。页面临时选择和请求中的中间计算不进入数据库。

「默认不」是因为反范式设计可以换取读取性能。代价是同一个事实有了多个来源，采用前要写清楚：哪个来源是权威数据，由哪段代码更新推导值、是否与权威数据在同一个事务里，不一致时怎样发现和修复。缓存和页面状态是同一事实的另一份副本，适用同样的要求。

先让逻辑正确，再优化性能。先把业务概念和表之间的关系建立清楚，概念稳定之后再考虑索引、缓存和冗余字段。大部分业务没有性能问题，过早加入这些手段只会增加数据同步和失效的负担。需要优化时，用真实查询和数据量找到慢的位置。查询次数随数据量增长（分页之后逐条查询关联数据）是逻辑问题，应当直接修正。

名称、字段和路由不同时保留两套含义相近的版本，否则调用方只能猜哪一套是当前约定。

## 旧入口退出之后

旧实现的调用方、数据迁移和回滚方案处理完之后，立即删除旧代码，源码只保留当前有效的名称和行为，历史由 Git 保存，不留转发入口和兼容分支。

发布周期不同的调用方例外，主要是 App 或其他无法跟随后端统一发布的客户端。兼容优先只在接入点处理；接入点处理不了，才逐步向更深的层次增加。
