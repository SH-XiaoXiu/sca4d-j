# 11 测试规范

先列出修改可能破坏的行为，再选择能验证这些行为的最小检查：类型用编译，业务规则用测试，Spring 装配用上下文检查，页面效果由开发者人工验收。每次都重读文件、检查 diff 并运行 `git diff --check`；文件覆盖和证据要求见[代码评审规范](/standards/12_review)。

## 选择能发现问题的检查

测试围绕本次修改可能破坏的契约选择。不把格式检查、编译、单元测试、集成测试和全项目测试组成每次变更的固定套餐。

每次修改都完整重读改动文件，检查 diff，运行 `git diff --check`，并对照真正相关的目录、命名、失败、安全和文档规则。

- 只改 Markdown 正文、注释、拼写或不影响产物的格式时，不运行 Java 编译、前端构建和业务测试。
- 修改 Java 类型、方法签名、导入或逻辑时，先编译直接受影响的 Gradle 项目。
- 修改局部行为时，优先运行对应类或对应契约的最小测试集。
- 修改公开接口时，检查直接使用该接口的项目；只有影响跨越多个模块时才扩大范围。
- 修改 Spring 装配、应用配置或启动流程时，运行最小上下文测试或启动检查。
- 修改数据库迁移时，使用临时数据库验证新库和已有数据库的受影响路径。
- 修改 TypeScript、Vue、Store 或 HTTP 契约时，先运行受影响 workspace 的类型检查，再根据变更选择相关测试。
- 只有前端入口、依赖、构建配置、生产资源或打包行为改变时才默认运行生产构建。
- 修改文档导航、链接、VitePress 配置或生成输入时运行文档构建。

全仓库编译和完整测试套件只用于确实影响全仓库的修改、正式发布验收或明确要求的场景。

## 各类测试的责任

单元测试检查无需 Spring 容器和真实外部依赖就能判断的业务规则、类型转换、编解码和失败结果。通过公开行为验证，不通过反射调用 private 方法。

集成测试检查真实的 Repository、Mapper、数据库约束、事务、消息、缓存和模块协作。测试要证明最终数据和副作用，不只检查方法已被调用。

Spring 装配测试检查自动配置条件、Bean 选择、配置绑定和启动失败。普通单元测试不能代替装配验证。

数据库测试检查迁移顺序、约束、索引、空值、默认值、数据回填、锁和失败恢复。不使用 H2 或手写 mock 代替 PostgreSQL 专有行为。

前端自动化测试覆盖权限判断、状态转换、数据校验、共享 Store 规则和 HTTP 错误转换。布局、样式、文案、响应式和交互感受由开发者人工验收。

E2E 只用于值得用真实边界保护的跨系统主流程。页面局部调整不为了证明视觉结果而新增脆弱的 DOM 尺寸断言。

## 测试数据

测试数据显式创建当前场景需要的对象、状态和关系。不依赖执行顺序、开发者本机残留数据或另一个测试的副作用。时间、随机数、ID 和外部返回需要稳定结果时，使用项目现有可控入口。

## 资源限制

编译、测试、文档构建和审计默认限制 CPU 与内存，不并行启动两个资源密集任务。

```bash
GRADLE_USER_HOME=/tmp/sca4dj-gradle \
GRADLE_OPTS='-Dorg.gradle.jvmargs=-Xmx1g -XX:MaxMetaspaceSize=384m' \
nice -n 10 ./gradlew --no-daemon --max-workers=1 :<project-path>:<task>
```

```bash
NODE_OPTIONS='--max-old-space-size=1024' nice -n 10 pnpm <command>
nice -n 10 pnpm exec vitest run <scope> --maxWorkers=1
```

## 变更文件

变更文件清单必须覆盖相关代码、迁移、配置、契约、前端、测试和文档，并与实际 `git diff` 一致，不包含遗漏或无关修改。

## 读取相关代码

文件验收覆盖完整职责、调用者和测试，不能只根据命中行或 diff 片段推断整体行为。

## 分层审查

验收范围包括业务语义与状态机、分层和依赖、类型与空值、SQL 和事务、认证权限、并发和集群、外部失败、前端状态、测试证据、文档同步。

Java 变更同时检查[命名、类型与代码结构](/standards/03_code-structure)和[注释、文档注释与日志](/standards/08_comments-and-logging)。改动类型必须位于可预测的领域或职责包；业务流程必须留下足以判断阶段、结果和恢复方式的日志。

## SQL 与调用数量

列表和聚合查询的验收证据必须包含 SQL 次数、N+1、全表扫描、索引、访问范围条件、版本条件和每批数量。测试数据库只有少量数据时，实际执行 SQL 仍属于验收范围。

## 多实例检查

使用本地内存、定时任务、连接注册表或提交后回调的实现，必须明确多个实例同时运行、同一任务重复执行、节点中途退出和节点恢复后的结果。

## 前端状态检查

前端验收覆盖加载、空、成功、失败、无权限、409、提交中、高风险确认、窄屏、键盘和可访问名称。静态截图不能证明交互已经完成。

## 验证范围

验证范围从直接相关测试扩展到模块测试和完整业务操作测试。测试证据必须包含目标分支和实际配置，不能只有命令退出码。

## 覆盖证据

每个验收项必须对应测试方法、HTTP 响应、SQL 行、消息或 Outbox 记录、日志 traceId、浏览器状态或构建产物。间接推断不构成验收证据。

## 提交条件

提交必须同时满足实现完整、旧路径删除、格式和测试通过、文档同步、无敏感信息且 diff 范围清晰。失败命令必须归类为代码问题、环境问题或覆盖缺口，不能从验收记录中省略。
